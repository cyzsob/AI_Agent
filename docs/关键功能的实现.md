### 1.3 PDF 文件解析（混合模式）

PDF 的解析是最复杂的，因为 PDF 可能同时包含**可选择文本**（文字型）和**图片中的文字**（扫描件/含截图）。

本项目实现了一个 **三层混合解析策略**：

#### 架构

```
PDF 文件
  │
  ├──→ PyMuPDF (fitz) 逐页提取可选择文本
  │       (page.get_text())
  │
  └──→ PyMuPDF 渲染每页为图像
          │
          └──→ RapidOCR 识别图片文字
                  (内置中英文模型，无需语言包)
                      │
                      智能合并策略：
                      ├ 文本 ≥ 80 字符 + 有 OCR  → 文本 + 图片 OCR 追加
                      ├ 文本 ≥ 80 字符 + 无 OCR  → 纯文本
                      ├ 文本 < 80 字符 + 有 OCR  → 纯 OCR（扫描件 PDF）
                      └ 两者都失败               → 返回有内容的那一路
```

#### 核心代码

```python
# parse_pdf.py — PDF 混合解析
import numpy as np
import fitz  # PyMuPDF

MIN_TEXT_LENGTH = 80  # 低于此值认为 PDF 以图片为主，优先使用 OCR

def parse_pdf(file_path: str) -> str:
    doc = fitz.open(file_path)
    text_parts, ocr_parts = [], []

    for page in doc:
        # ---- 提取可选择文本 ----
        page_text = page.get_text().strip()
        if page_text:
            text_parts.append(page_text)

        # ---- 渲染为图片 + OCR ----
        pix = page.get_pixmap(matrix=fitz.Matrix(2.0, 2.0))  # 2x 分辨率
        img = np.frombuffer(pix.samples, dtype=np.uint8).reshape(
            pix.height, pix.width, pix.n
        )
        if pix.n == 4:
            img = img[:, :, :3]  # RGBA → RGB
        ocr_page_text = _ocr_page(img)
        if ocr_page_text:
            ocr_parts.append(ocr_page_text)

    return merge_text("\n".join(text_parts), "\n\n".join(ocr_parts))
```

#### 智能合并

```python
# parse_pdf.py — merge_text（逻辑与 Node 版 mergeText 一致）
def merge_text(text_content: str, ocr_text: str) -> str:
    text_len = len(text_content or "")
    ocr_len = len(ocr_text or "")

    if text_len >= MIN_TEXT_LENGTH and ocr_len > 0:
        # 文字型 PDF + 含图片：合并两者，用分隔符标明
        return text_content + "\n\n--- 以下为图片 OCR 内容 ---\n" + ocr_text
    elif text_len >= MIN_TEXT_LENGTH:
        return text_content          # 文字型 PDF，无 OCR 内容
    elif ocr_len > 0:
        return ocr_text              # 图片型 PDF（扫描件），优先使用 OCR
    else:
        return text_content or ocr_text or ""  # 两路均失败，返回有内容的一路
```

#### 关键依赖

| 包                | 版本      | 用途                               | 平台兼容                 |
| ----------------- | --------- | ---------------------------------- | ------------------------ |
| `pymupdf` (fitz)  | ≥1.24     | PDF 解析、文本提取、页面渲染       | ✅ 纯 Python + 预编译二进制 |
| `rapidocr`        | ≥2.0      | OCR 文字识别（内置中英文模型）     | ✅ 基于 onnxruntime，无需训练数据 |
| `numpy`           | ≥1.26     | 图像数组转换与通道处理             | ✅ 预编译二进制          |
| `python-docx`     | ≥1.1      | DOCX 文档解析                      | ✅ 纯 Python             |

#### 技术要点

- **PyMuPDF 一库多用**：同时承担文本提取（`page.get_text()`）和页面渲染（`get_pixmap()`），无需额外的 pdfjs worker，无版本冲突问题
- **2x 缩放渲染**：`fitz.Matrix(2.0, 2.0)` 以 2 倍分辨率渲染页面，显著提升小字体的 OCR 识别率
- **RGBA → RGB**：RapidOCR 需要 3 通道输入，`pix.n == 4` 时截取前 3 通道
- **OCR 引擎复用**：模型加载耗时数秒，使用模块级单例 + 惰性初始化，避免每次解析都重新加载
- **兼容 rapidocr 2.x / 3.x**：`_ocr_page` 同时兼容 `(result, elapse)` 元组和 `RapidOCROutput` 对象两种返回格式
- **内置语言模型**：RapidOCR 内置中英文识别，无需像 Tesseract 那样准备 `chi_sim.traineddata` 语言包

### 实现位置

### 实现代码

```python
# ingest.py — 文档分块（逐文件进行）
from langchain_text_splitters import RecursiveCharacterTextSplitter

splitter = RecursiveCharacterTextSplitter(
    chunk_size=200,
    chunk_overlap=20,
)

raw_doc = Document(page_content=content, metadata={"source": rel})
chunks = splitter.split_documents([raw_doc])

# 写入增强元数据（便于诊断与按文件清理）
for i, chunk in enumerate(chunks):
    chunk.metadata.update({
        "file_hash": sha,
        "chunk_index": i,
        "total_chunks": len(chunks),
    })
```

### 核心参数

| 参数           | 值  | 说明                                                     |
| -------------- | --- | -------------------------------------------------------- |
| `chunk_size`   | 200 | 每个块的最大字符数。保证块足够小，便于精确检索           |
| `chunk_overlap`| 20  | 相邻块之间的重叠字符数。防止一个完整语义被切分到两个块中 |

### 分块流程

```
原始文档（完整内容）
  → RecursiveCharacterTextSplitter
    → 首先按 "\n\n"（段落分隔）尝试分割
    → 如果块仍大于 chunk_size，按 "\n"（行分隔）继续分割
    → 如果还大，按 句号/问号等（句分隔）继续分割
    → 最后按 空格 或 字符 粒度分割
  → 输出 N 个 Document 对象，每个包含 page_content + metadata
```

### 数据持久化

使用 `PGVector.add_documents()` 将分块向量化后存入 PostgreSQL：

```python
# ingest.py — 嵌入模型 + 向量库初始化
from langchain_ollama import OllamaEmbeddings
from langchain_postgres import PGVector

embeddings = OllamaEmbeddings(
    model="bge-m3",                # 中英文优化的嵌入模型
    base_url="http://localhost:11434",  # 本地 Ollama 服务
)

vector_store = PGVector(
    embeddings=embeddings,
    collection_name="documents",
    connection="postgresql+psycopg://user:pass@host:5432/dbname",
    use_jsonb=True,
)
```

每个文件的入库流水线为 **删旧 → 嵌入入库 → 更新注册表**：

```python
# ingest.py — 单个文件入库流水线
import uuid

# 1) 先删除该文件的旧 chunks（按 cmetadata->>'source' 定位，新增时无旧数据无副作用）
delete_chunks_by_source(conn, rel)
conn.commit()

# 2) 向量化 + 入库
vector_store.add_documents(chunks, ids=[str(uuid.uuid4()) for _ in chunks])

# 3) 更新文件注册表（记录内容指纹，供下次增量判断）
upsert_registry(conn, rel, sha, file_path.stat().st_size, len(chunks))
conn.commit()
```

`langchain_postgres` 的 PGVector 实际写入两张表：

- `langchain_pg_collection`：集合表，记录 `name="documents"`
- `langchain_pg_embedding`：向量表，每行包含 `id`、`collection_id`、`document`（文本）、`cmetadata`（JSON 元数据）、`embedding`（bge-m3 生成的 1024 维向量）

> **注意**：后续 BM25 索引构建（见第三节）正是从 `langchain_pg_embedding` 表读取数据，两处数据源必须一致。

### 增量同步机制（新增 / 更新 / 删除文档）

以文件内容 **sha256 指纹** + 注册表表 `doc_file_registry`，将入库从"全量重灌"改造为**幂等增量同步**：

| 场景     | 判断依据                 | 处理方式                                            |
| -------- | ------------------------ | --------------------------------------------------- |
| 新增文档 | 路径不在注册表中         | 解析 → 分块 → 嵌入入库 → 写入注册表                 |
| 修改文档 | 路径在但内容哈希不一致   | 先删旧 chunks → 重新分块嵌入 → 更新注册表哈希       |
| 删除文档 | 注册表有、磁盘已消失     | 仅 `--prune` 时：删 chunks + 删注册表行             |
| 未变化   | 路径与内容哈希都一致     | 跳过（幂等）                                        |

注册表表结构（ingest.py 内 `CREATE TABLE IF NOT EXISTS` 幂等建表）：

```sql
CREATE TABLE IF NOT EXISTS doc_file_registry (
    file_path   TEXT PRIMARY KEY,          -- 相对 documents/ 的路径（当前即文件名）
    file_hash   TEXT NOT NULL,             -- sha256(文件字节)
    file_size   BIGINT NOT NULL,           -- 文件字节数
    chunk_count INT  NOT NULL DEFAULT 0,   -- 该文件生成的 chunk 数
    updated_at  TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

CLI 参数：

| 参数        | 说明                                                           |
| ----------- | -------------------------------------------------------------- |
| （无参数）  | 默认增量同步（幂等），只处理新增/修改的文件                     |
| `--rebuild` | 先清空向量库与注册表，再全量重建（schema/嵌入模型变更时使用）   |
| `--prune`   | 清理磁盘上已删除文档对应的 chunks 与注册表记录（默认关闭，防误删） |

> **升级兼容性**：首次运行增量同步时注册表为空，所有文件都会当作"新增"处理；而新增路径会**先按 source 删旧 chunks 再插入**，因此历史重复/旧版本数据会被自动清理，无需手工清库。

## 三、混合检索 (Hybrid Search)

### 实现位置

[hybrid_retriever.py](file:///d:/AiAgent/my-rag-demo/hybrid_retriever.py) + [reranker.py](file:///d:/AiAgent/my-rag-demo/reranker.py)

### 整体架构

```
用户查询
  │
  ├──→ 向量检索 (PGVector + bge-m3)     →  按语义相似度排序
  │

```

### 3.2 BM25 检索

使用 `rank_bm25` 的 `BM25Okapi` 实现，纯 Python、零外部依赖。

```python
# hybrid_retriever.py — 中文分词
import re

def tokenize_for_bm25(text: str) -> str:
    """在中文汉字之间插入空格，使 BM25 将每个汉字作为独立 token 索引。
    英文/数字保持原样，按空格分词。"""
    text = re.sub(r"([\u4e00-\u9fff\u3400-\u4dbf\uf900-\ufaff])", r" \1 ", text)
    text = re.sub(r"\s+", " ", text)
    return text.strip().lower()
```

```python
# hybrid_retriever.py — BM25 检索器
import numpy as np
from rank_bm25 import BM25Okapi

class BM25Retriever(BaseRetriever):
    def __init__(self, bm25_index: BM25Okapi, doc_map: dict, k: int = 6):
        super().__init__()
        self._bm25 = bm25_index
        self._doc_map = doc_map
        self._k = k

    async def _get_relevant_documents(self, query: str, **kwargs):
        processed_query = tokenize_for_bm25(query).split()
        scores = self._bm25.get_scores(processed_query)

        top_indices = np.argsort(scores)[::-1][: self._k]
        docs = []
        for idx in top_indices:
            if scores[idx] <= 0:
                continue
            doc_id = list(self._doc_map.keys())[idx]
            doc_data = self._doc_map[doc_id]
            docs.append(Document(
                page_content=doc_data["pageContent"],
                metadata={**doc_data["metadata"], "bm25Score": float(scores[idx])},
            ))
        return docs
```

**技术要点**：

- **为什么选 rank_bm25**：纯 Python 实现，零外部依赖，原生实现 Okapi BM25 算法，适合 demo 数据量级
- **中文分词策略**：在汉字前后插入空格，使每个汉字作为独立 token 索引。这是针对中文 BM25 的合理近似，能有效匹配关键词中的字序列
- **内存索引**：服务启动时从数据库加载全部文档，在内存中构建 BM25 索引（`BM25Okapi(tokenized_corpus)`），每次查询直接计算得分，速度快
- **零分过滤**：得分 ≤ 0 的文档直接跳过（BM25 对完全不匹配的词返回 0）

### 3.3 RRF 融合 (Reciprocal Rank Fusion)

```python
# hybrid_retriever.py — RRF 融合
import hashlib

def _doc_key(doc: Document) -> str:
    """统一的文档去重键：基于内容哈希。

    向量检索返回的 doc 无 dbId（metadata 仅为入库时的 cmetadata），
    BM25 检索返回的 doc 有 dbId，同一 chunk 在两路的键必须一致才能正确去重，
    因此统一使用内容哈希而非 dbId / 内容前缀。"""
    return hashlib.md5(doc.page_content.encode("utf-8")).hexdigest()


def rrf_merge(vector_docs, bm25_docs, final_k=3, rrf_k=60,
              vector_weight=0.5, bm25_weight=0.5):
    score_map = {}

    # 向量结果：按排名打分
    for i, doc in enumerate(vector_docs):
        doc_id = _doc_key(doc)
        if doc_id not in score_map:
            score_map[doc_id] = {"doc": doc, "score": 0.0}
        score_map[doc_id]["score"] += vector_weight / (rrf_k + i + 1)

    # BM25 结果：按排名打分
    for i, doc in enumerate(bm25_docs):
        doc_id = _doc_key(doc)
        if doc_id not in score_map:
            score_map[doc_id] = {"doc": doc, "score": 0.0}
        score_map[doc_id]["score"] += bm25_weight / (rrf_k + i + 1)

    # 按融合得分降序排列，并把融合分写回 doc 元数据（便于诊断）
    merged = sorted(score_map.values(), key=lambda x: x["score"], reverse=True)
    for item in merged:
        item["doc"].metadata["rrfScore"] = item["score"]

    return [item["doc"] for item in merged[:final_k]]
```

**RRF 公式**：

```
score(doc) = vectorWeight / (rrfK + rank_vector) + bm25Weight / (rrfK + rank_bm25)
```

**默认参数**：

| 参数            | 值  | 说明                                        |
| --------------- | --- | ------------------------------------------- |
| `rrfK`          | 60  | 融合常数，防止排名差异过大的文档得分趋近于0 |
| `vectorWeight`  | 0.5 | 向量检索权重                                |
| `bm25Weight`    | 0.5 | BM25 检索权重                               |
| `vectorK`       | 6   | 向量检索取 Top-6（agent.py 中配置为 10）    |
| `bm25K`         | 6   | BM25 检索取 Top-6（agent.py 中配置为 10）   |
| `rerankCandidates` | 10 | 融合后交给重排器的候选池大小                |
| `finalK`        | 3   | 重排后最终返回 Top-3                        |

**为什么 RRF 有效**：

- 一个文档同时在两路检索中排名靠前时，融合得分会叠加，排名更高
- 向量检索擅长**语义匹配**（"AI 公司的开源策略" → 命中"MIT 协议"相关段落）
- BM25 擅长**关键词精确匹配**（"DeepSeek-V4" → 精确命中包含该词组的段落）
- RRF 融合取两者之长，即使某一路检索表现差，另一路也能兜底

**Python 版与 JS 版的去重差异**：JS 版使用 `metadata.dbId` 或内容前缀作为去重键；Python 版统一使用 **内容 MD5 哈希**，因为向量检索返回的 doc 不带 `dbId`，两路的键必须一致才能正确去重。

### 3.4 Cross-Encoder 重排（新增能力）

重排是 Python 版新增的一层，弥补 bi-encoder（bge-m3）无法细粒度比较候选片段的不足：

```python
# reranker.py — Cross-Encoder 重排器
from sentence_transformers import CrossEncoder

class CrossEncoderReranker:
    def __init__(self, model_name="BAAI/bge-reranker-base",
                 max_length=512, batch_size=16, device=None):
        self._model_name = model_name
        self._max_length = max_length
        self._batch_size = batch_size
        self._device = device
        self._model = None  # 惰性加载，首次调用时从 HuggingFace 下载权重

    async def rerank(self, query, docs, top_k=None):
        if not docs:
            return []
        try:
            scores = await asyncio.to_thread(self._predict, query, docs)
        except Exception as err:
            print(f"[Reranker] 重排失败，按原顺序返回候选: {err}")
            return docs  # 兜底：重排失败不拖垮主流程

        ranked = sorted(zip(scores, docs), key=lambda pair: pair[0], reverse=True)
        ordered = []
        for score, doc in ranked:
            doc.metadata["rerankScore"] = score
            ordered.append(doc)
        return ordered[:top_k] if top_k else ordered
```

**技术要点**：

- **逐对打分**：将 `(query, doc.page_content)` 组成 pair 输入 CrossEncoder，直接输出相关性分数，比 bi-encoder 更精细
- **惰性加载**：`_model` 首次调用才加载（需下载权重），避免服务启动变慢
- **失败兜底**：模型加载或推理失败时打印警告并按原顺序返回，保证 RAG 主流程不被重排拖垮
- **线程池**：`CrossEncoder.predict` 是同步阻塞调用，用 `asyncio.to_thread` 放入线程池

### 3.5 混合检索器并行执行 + 重排

```python
# hybrid_retriever.py — HybridRetriever._get_relevant_documents
async def _get_relevant_documents(self, query, **kwargs):
    # 并行执行向量检索（sync→线程池）和 BM25 检索（async）
    vector_docs, bm25_docs = await asyncio.gather(
        asyncio.to_thread(self._vector_store.similarity_search, query, k=self._vector_k),
        self._bm25_retriever._get_relevant_documents(query),
    )

    # RRF 融合 → 候选池（不直接截断到 final_k，先放大候选供重排）
    candidates = rrf_merge(
        vector_docs, bm25_docs,
        final_k=self._rerank_candidates,   # 先取 10 条候选
        rrf_k=self._rrf_k,
        vector_weight=self._vector_weight,
        bm25_weight=self._bm25_weight,
    )

    # Cross-Encoder 重排（可选）→ 最终 Top-K
    if self._enable_rerank and self._reranker is not None and candidates:
        return await self._reranker.rerank(query, candidates, top_k=self._final_k)

    return candidates[: self._final_k]
```

**关键设计**：

- **`asyncio.gather` 并行执行两路检索**，相互等待而非串行，总耗时 ≈ max(向量检索, BM25 检索)
- **候选池放大**：RRF 融合先取 `rerankCandidates=10` 条，而不是直接截断到 3 条，给重排器更多候选做精细排序
- **两级排序流水线**：`向量/BM25 各自 Top-10 → RRF 融合 Top-10 → Cross-Encoder 重排 Top-3`

```python
async def rewrite_step(user_input: str):

        "context": "\n\n".join(doc.page_content for doc in docs),
```

### 实现位置

- [multi_agent.py](file:///d:/AiAgent/my-rag-demo/multi_agent.py) — Supervisor 多 Agent 图的构建（状态定义、路由工具、supervisor 节点、worker 装配）

### 5.1 整体思路

本项目将"单 ReAct Agent（一个模型 + 全部工具混杂）"升级为 **Supervisor 监督者模式的多 Agent 系统**（不新增任何依赖，基于已安装的 `langgraph` 手写 StateGraph 实现）：

- 一个 **Supervisor 协调 Agent**：只负责路由，把请求分发给最合适的专业 worker，并在 worker 完成后决定继续或结束（`finish_workflow`）。supervisor 不持有业务工具、不回答问题。
- 三个 **专业 worker Agent**（按工具域划分，各持独立工具子集 + 领域专用提示词）：

| worker 节点 | 职责 | 持有工具 |
| ----------- | ---- | -------- |
| `knowledge` | 知识/检索 | `get_deepseek_info`、`search_kb` |
| `devops`    | Gitee 平台操作 | `gitee_*` 等 MCP 工具 |
| `general`   | 天气 + 日常闲聊 | `get_weather` |

核心收益：每个 worker 只面对自己领域的少量工具，LLM 决策更聚焦、误调工具概率更低；提示词可按领域深度定制；新增专业 Agent 时只需加一个节点。

### 5.6 Supervisor 图结构（multi_agent.py）

[multi_agent.py](file:///d:/AiAgent/my-rag-demo/multi_agent.py) 用 `StateGraph` 手写监督者图（不依赖 `langgraph-supervisor` 等额外包）：

```
        START
          │
          ▼
   ┌─ supervisor（协调 Agent，只持有路由工具）────────┐
   │  TransferToKnowledge / TransferToDevops /       │
   │  TransferToGeneral / finish_workflow            │
   └───────┬────────────────┬────────────────┬───────┘
           ▼                ▼                ▼
      knowledge          devops           general
      (RAG 工具)        (MCP 工具)       (天气+闲聊)
      ReAct Agent       ReAct Agent      ReAct Agent
           └──────────────┴────────────────┘
                    │ 完成后回到 supervisor
                    ▼
              END / 再次路由
```

核心实现要点：

1. **路由工具**（[multi_agent.py#L34-L61](file:///d:/AiAgent/my-rag-demo/multi_agent.py#L34-L61)）：为每个成员生成 `TransferToXxx` 占位工具 + `finish_workflow`，仅用于触发路由，函数体不被真正执行。`tool_to_node` 显式映射 `{"TransferToKnowledge": "knowledge", ...}`。

2. **supervisor 节点内直接路由**（`Command(goto=...)`，替代条件边）：模型绑定路由工具调用后，**为每个 tool_call 合成对应的 ToolMessage**（否则下游 worker 的 LLM 校验会报 `INVALID_CHAT_HISTORY`），然后返回 `Command(goto=目标节点, update={"messages": [...]})` 直接跳转：

```python
# multi_agent.py — supervisor 节点核心
async def supervisor_node(state: MultiAgentState):
    response = await model.bind_tools(transfer_tools).ainvoke([sys_msg, *state["messages"]])

    tool_calls = getattr(response, "tool_calls", None) or []
    tool_messages = [
        ToolMessage(content=f"任务已转交给 {tc['name']}", tool_call_id=tc["id"])
        for tc in tool_calls
    ]

    if not tool_calls or tool_calls[0]["name"] == "finish_workflow":
        goto = END
    else:
        goto = tool_to_node.get(tool_calls[0]["name"], END)

    return Command(goto=goto, update={"messages": [response, *tool_messages]})
```

3. **worker 装配**：每个 worker 是独立的 `create_react_agent(model, tools=该域工具子集, prompt=_worker_prompt(node))`，完成后通过 `graph.add_edge(node, "supervisor")` 把控制权交回 supervisor（可再路由或结束）。无工具的节点自动跳过（如未配置 MCP 时 devops 不建节点，supervisor 成员列表同步剔除）。

### 5.7 Supervisor 路由推理循环

```
用户: "DeepSeek V4 用什么架构？"
  → supervisor 判定属于"知识/检索" → TransferToKnowledge
  → knowledge worker 调用 search_kb({ query: "DeepSeek V4 架构" })
    → 混合检索：向量 + BM25 → RRF → Cross-Encoder 重排 → 返回 top-3 片段
  → 回到 supervisor → finish_workflow → END

用户: "DeepSeek 开源战略怎么样？"
  → supervisor → TransferToKnowledge
  → knowledge worker 调用 get_deepseek_info()
  → 读取 deepseek介绍手册.txt 全文返回 → 整合信息生成回答 → 回到 supervisor → END

  → supervisor → TransferToGeneral → general worker 直接回答，无工具调用 → END

用户: "北京今天天气怎么样？"
  → supervisor → TransferToGeneral
  → general worker 调用 get_weather({ city: "北京" })
  → 调用 OpenWeatherMap API 获取实时数据 → 整合天气数据生成回答 → END

  → devops worker 输出 tool_call: gitee_* → MCP Server 执行 → 返回结果 → END
```

**多 Agent 的优势**：

- **路由聚焦**：supervisor 只做分发，每个 worker 只面对本域少量工具，决策更稳定、误调工具概率更低
- **避免不必要的 token 消耗**：闲聊类问题直接由 general 回答，无需检索
- **按域定制提示词**：每个 worker 的 prompt 独立定制（如 knowledge 强制区分"公司整体"与"技术细节"两种工具）
- **灵活扩展**：新增专业 Agent 只需在 `multi_agent.py` 加一个节点 + `_worker_prompt`，在 `agent.py` 分组处补充工具前缀

```
  ├─ TOOL_CALL_ARGS            → (可选) 工具参数字典
  ├─ TOOL_CALL_RESULT          → (可选) 工具执行结果
  ├─ TOOL_CALL_END             → (可选) 工具生命周期结束
  │
  ├─ TEXT_MESSAGE_START        → 文本回复开始
  ├─ TEXT_MESSAGE_CONTENT      → 逐 token 推送文本内容（多次）
  ├─ TEXT_MESSAGE_END          → 文本回复结束
  │
RUN_FINISHED                   → 全部处理完成
```

### 6.3 聊天端点（核心流式处理）

多 Agent 图与单 Agent 的 `astream` 接口完全兼容，流式循环按"节点 + 消息类型"处理：

```python
# server_agui.py — POST /api/chat（SSE 事件流，多节点适配）
SUPERVISOR_NODE = "supervisor"
TRANSFER_TOOL_NAMES = {"finish_workflow", "TransferToKnowledge",
                       "TransferToDevops", "TransferToGeneral"}

@app.post("/api/chat")
async def chat(request: Request):
    body = await request.json()
    thread_id = body.get("threadId")
    run_id = body.get("runId")
    messages = body.get("messages", [])

    async def event_stream():
        yield sse_event({"type": AgUiEventType.RUN_STARTED, "threadId": thread_id, "runId": run_id})

        # 多轮对话：加载历史 + 构造完整消息
        user_message_record = {"role": "user", "content": user_message}
        history = get_or_create_history(thread_id)
        full_messages = [*to_langchain_messages(history), user_message_record]

        # 多 Agent 图流式执行（stream_mode="messages"）
        stream = _agent.astream({"messages": full_messages}, stream_mode="messages")

        async for chunk, metadata in stream:
            node_name = metadata.get("langgraph_node") if metadata else None

            # ① Supervisor 节点：仅内部路由，不透出事件、不进入历史
            if node_name == SUPERVISOR_NODE:
                continue

            # ② 工具执行结果（ToolMessage）：只按消息类型判断，不依赖节点名
            #    （嵌套子图下工具消息的节点名可能上报为外层节点名）
            if isinstance(chunk, ToolMessage):
                yield sse_event({"type": AgUiEventType.TOOL_CALL_RESULT, ...})
                yield sse_event({"type": AgUiEventType.TOOL_CALL_END, ...})
                continue

            # ③ Worker 节点输出（文本 + 工具调用）
            #    注意：嵌套子图下 worker 输出是完整 AIMessage（非 AIMessageChunk），
            #    AIMessageChunk 是 AIMessage 的子类，统一按 AIMessage 处理
            if isinstance(chunk, AIMessage):
                # ... 工具调用 → TOOL_CALL_START / TOOL_CALL_ARGS
                #     （iter_tool_call_pieces 提取，路由工具名兜底过滤）
                # ... 文本内容 → TEXT_MESSAGE_START / TEXT_MESSAGE_CONTENT（逐 token）

        # 流结束后：保存本轮消息到历史 → 发送 TEXT_MESSAGE_END / RUN_FINISHED

    return StreamingResponse(event_stream(), media_type="text/event-stream")
```

**多节点适配的三个关键点**：

1. **supervisor 不透出**：supervisor 内部的路由 tool_call（`TransferToXxx`/`finish_workflow`）属于编排逻辑，不推给客户端、不进入会话历史，直接 `continue` 跳过。
2. **工具消息去节点名依赖**：工具执行结果只按 `isinstance(chunk, ToolMessage)` 判断（原 `node_name == "tools"` 在嵌套子图下不可靠）。
3. **Worker 输出统一按 `AIMessage` 处理**：当前 langgraph 版本中嵌套 subgraph 的 worker 输出是**完整 `AIMessage`**（含 dict 形态的 `tool_calls`）而非流式 `AIMessageChunk`，因此统一按 `AIMessage` 分支处理，并借助辅助函数 `iter_tool_call_pieces(chunk)` 兼容两种形态（`tool_call_chunks` / `tool_calls`，每项可能是 dict 或对象）。

### 6.4 TOOL_CALL_ARGS 的缓冲机制

由于工具参数可能是逐 token 产生的流式片段，也可能是 worker 一次性输出的完整 dict，直接发送会导致前端收到碎片化 JSON。通过 **累积 args 缓冲区** + **JSON 完整性检测**，只在 args 完整时才一次性发送；**缓冲区改为按 `tool_call_id`（UUID，全局唯一）键控**，避免多节点下 index 从 0 重复导致的混叠：

```python
# server_agui.py — 缓冲累积（按 tool_call_id 键控）
tool_call_ids = set()        # 已发送 TOOL_CALL_START 的 tool_call_id
tool_call_args_buffer = {}   # tool_call_id -> 流式 args 累积（发送后清空）
tool_call_full_args = {}     # tool_call_id -> 完整 args（供保存历史，不清空）
tool_call_name_buffer = {}   # tool_call_id -> 工具名

for tc_id, tc_name, tc_args in iter_tool_call_pieces(chunk):
    # 兜底过滤：路由工具不透出
    if tc_name in TRANSFER_TOOL_NAMES:
        continue

    # TOOL_CALL_START — 只在首次出现时发送
    if tc_id and tc_id not in tool_call_ids:
        tool_call_ids.add(tc_id)
        yield sse_event({"type": AgUiEventType.TOOL_CALL_START,
                         "toolCallId": tc_id, "toolCallName": tc_name})

    if tc_id and tc_args:
        args_str = json.dumps(tc_args, ensure_ascii=False) if isinstance(tc_args, dict) else tc_args
        tool_call_args_buffer[tc_id] = tool_call_args_buffer.get(tc_id, "") + args_str
        tool_call_full_args[tc_id] = tool_call_full_args.get(tc_id, "") + args_str

# 检测 JSON 是否完整 → 一次性发送（发送后清空流式缓冲）
for tc_id, accumulated_args in tool_call_args_buffer.items():
    try:
        json.loads(accumulated_args)      # 验证 JSON 是否完整
        yield sse_event({"type": AgUiEventType.TOOL_CALL_ARGS,
                         "toolCallId": tc_id, "delta": accumulated_args})
        tool_call_args_buffer.pop(tc_id, None)
    except (json.JSONDecodeError, ValueError):
        pass                              # JSON 尚未完整，继续缓冲
```

### 关键技术亮点总结

1. **多 Agent 协同（Supervisor 监督者模式）** — 一个 supervisor 只做路由分发，三个专业 worker（知识/DevOps/通用）各持工具子集与领域提示词；`Command(goto=...)` 节点内路由 + 合成 ToolMessage 保证消息历史合法
2. **混合检索 (向量 + BM25 + RRF + Cross-Encoder 重排)** — 兼顾语义匹配和关键词精确匹配，两路并行执行 + 加权排名融合 + 交叉编码器精排
3. **Worker 自主决策（ReAct）** — 每个 worker 是 LangGraph ReAct Agent，按工具返回内容自主回答，告别固定链路
4. **Query Rewriting** — 用 LLM 将口语化问题改写为检索友好表达，提升检索准确率
5. **RRF 融合算法** — 按排名倒数加权，消除两路检索评分尺度不一致的问题
6. **SSE 流式输出** — 逐 token 推送，支持工具调用事件和文本内容的实时渲染；supervisor 内部路由事件不透出
7. **本地嵌入** — Ollama + bge-m3 本地运行，零外部 API 依赖，低延迟
8. **MCP 标准化工具接入** — 通过 MCP 协议统一接入外部工具，配置文件驱动，零代码扩展；自动发现工具列表并包装为 LangChain StructuredTool
9. **基于 threadId 的多轮对话** — 会话历史管理器自动保存每轮对话消息（用户输入、工具调用、AI 回答），支持追问和指代消解；FIFO 上下文窗口策略防止 Token 溢出
10. **文档增量同步入库** — 以文件内容 sha256 为指纹 + 注册表表，新增/修改/删除文档幂等增量入库；`POST /api/admin/sync` + `refresh_retriever()` 让运行中的服务无需重启即可检索最新数据

JSON Schema → Pydantic 的转换（[mcp_client.py#L19-L58](file:///d:/AiAgent/my-rag-demo/mcp_client.py#L19-L58)）：

```python
def json_schema_to_pydantic(input_schema: dict) -> type[BaseModel]:
    """将 MCP 的 JSON Schema 参数定义转为 Pydantic model"""
    if not input_schema or "properties" not in input_schema:
        return create_model("EmptyInput")

    properties = input_schema.get("properties", {})
    required_fields = input_schema.get("required", [])

    fields = {}
    for key, prop in properties.items():
        prop_type = prop.get("type", "string")
        description = prop.get("description", "")
        is_required = key in required_fields

        # JSON Schema 类型 → Python 类型
        py_type = {"string": str, "number": float, "integer": int,
                   "boolean": bool, "array": list, "object": dict}.get(prop_type, str)

        if is_required:
            fields[key] = (py_type, Field(description=description))
        else:
            fields[key] = (py_type, Field(default=None, description=description))

    return create_model("ToolInput", **fields)
```

**关键技术点**：

| 步骤            | 说明                                                                                           |
| --------------- | ---------------------------------------------------------------------------------------------- |
| **加前缀**      | 防止不同 MCP Server 的工具名冲突（如 gitee_* 与 github_*）                   |


## 九、Agent 多轮对话详解

### 实现位置

[conversation_history.py](file:///d:/AiAgent/my-rag-demo/conversation_history.py) + [server_agui.py](file:///d:/AiAgent/my-rag-demo/server_agui.py)

### 9.1 问题背景

改造前，服务器每次请求都只将最后一条 user 消息传给 Agent：

```python
# 改造前 — 无历史记忆
stream = _agent.astream(
    {"messages": [{"role": "user", "content": user_message}]},
    stream_mode="messages",
)
```

这导致 Agent 每次对话都是"第一次见面"，无法理解"它"、"那个"等指代，也无法支持追问。

### 9.2 解决方案：基于 threadId 的历史管理

实现核心思路：

```
Turn 1:
  客户端 POST { threadId: "sess-1", messages: [user_msg_1] }
    → 历史为空 → 仅传 user_msg_1 给 Agent
    → Agent 执行 → 收集本轮消息 → 保存到会话历史

Turn 2:
  客户端 POST { threadId: "sess-1", messages: [user_msg_2] }
    → 加载历史 [user_msg_1, ai_msg_1, ...]
    → 构造完整消息 [user_msg_1, ai_msg_1, user_msg_2] 传给 Agent
    → Agent 理解上下文 → 收集本轮消息 → 追加到会话历史
```

### 9.3 关键步骤

#### 步骤 1：会话历史管理器

[conversation_history.py](file:///d:/AiAgent/my-rag-demo/conversation_history.py) 提供核心数据结构：

```python
# 内存存储结构
_sessions: dict[str, list[dict]] = {}   # dict[threadId, list[MessageRecord]]

# MessageRecord 格式（可序列化的 plain dict）
{
  "role": "user" | "assistant" | "tool",
  "content": str,
  # assistant 消息带工具调用时
  "tool_calls": [{"id", "name", "args"}] | None,
  # tool 消息带工具调用 ID
  "tool_call_id": str | None,
}
```

导出的函数：

| 函数                                 | 说明                                             |
| ------------------------------------ | ------------------------------------------------ |
| `get_or_create_history(thread_id)`   | 获取或创建会话历史                               |
| `to_langchain_messages(records)`     | 将 `MessageRecord[]` 转为 Agent 可接受的输入格式 |
| `append_messages(thread_id, messages)` | 追加本轮消息到历史（自动裁剪超出上限的旧消息） |
| `clear_history(thread_id)`           | 清除指定会话的历史                               |

**上下文窗口管理**：

```python
# conversation_history.py#L17
MAX_HISTORY_LENGTH = 20   # 保留最近 20 条消息（约 10 轮对话）

# append_messages 中的自动裁剪逻辑
def append_messages(thread_id: str, messages: list[dict]) -> None:
    history = get_or_create_history(thread_id)
    history.extend(messages)
    if len(history) > MAX_HISTORY_LENGTH:
        excess = len(history) - MAX_HISTORY_LENGTH
        _sessions[thread_id] = history[excess:]  # 丢弃最早的消息（FIFO）
```

#### 步骤 2：加载历史 + 构造完整消息

[server_agui.py#L147-L150](file:///d:/AiAgent/my-rag-demo/server_agui.py#L147-L150) — 在每次请求时加载历史并构造完整消息数组：

```python
# 1. 新建本轮 user 消息记录
user_message_record = {"role": "user", "content": user_message}

# 2. 获取该 threadId 的对话历史
history = get_or_create_history(thread_id)

# 3. 构造完整消息数组：[历史消息..., 新user消息]
full_messages = [*to_langchain_messages(history), user_message_record]
```

如果 `history` 为空（首次对话），`full_messages` 仅包含新消息。

#### 步骤 3：传递完整消息给 Agent

[server_agui.py#L164-L167](file:///d:/AiAgent/my-rag-demo/server_agui.py#L164-L167) — 将包含历史记录的完整消息数组传给 Agent：

```python
stream = _agent.astream(
    {"messages": full_messages},   # 包含所有历史上下文
    stream_mode="messages",
)
```

LangGraph 的多 Agent 图（supervisor + 各 `create_react_agent` worker）原生支持消息数组格式 — 消息按顺序排列，LLM 能感知全部历史上下文。

#### 步骤 4：从流中收集本轮消息

在现有的 stream 循环中增加收集逻辑：

```python

    final_content += chunk_content
    # ... 原有的 SSE 发送逻辑不变 ...

    tool_messages.append({
        "role": "tool",
        "content": chunk.content,
        "tool_call_id": chunk.tool_call_id,
    })
    # ... 原有的 SSE 发送逻辑不变 ...
```

#### 步骤 5：保存本轮消息到历史

[server_agui.py#L373-L414](file:///d:/AiAgent/my-rag-demo/server_agui.py#L373-L414) — 流结束后，构造本轮消息并保存（多 Agent 下同样按 `tool_call_id` 键控，无 index 冲突）：

```python
turn_messages = []

# 1) 用户消息
turn_messages.append(user_message_record)

# 2) 工具调用记录（按 tool_call_id 键控，多节点下无 index 冲突）
if tool_call_ids:
    tool_calls = []
    captured_args = dict(tool_call_full_args)   # 完整 args 缓冲，发送后不清空，供历史保存
    for tc_id, args in captured_args.items():
        parsed_args = json.loads(args) if isinstance(args, str) else args
        tool_calls.append({
            "id": tc_id,
            "name": tool_call_name_buffer.get(tc_id, ""),
            "args": parsed_args,
        })
    if not tool_calls:   # 兜底：有 tool_call_id 但无 args 缓冲
        for tc_id in tool_call_ids:
            tool_calls.append({
                "id": tc_id,
                "name": tool_call_name_buffer.get(tc_id, ""),
                "args": {},
            })
    turn_messages.append({
        "role": "assistant",
        "content": "",
        "tool_calls": tool_calls,
    })

# 3) 工具返回结果
turn_messages.extend(tool_messages)

# 4) AI 最终回答
if final_content:
    turn_messages.append({
        "role": "assistant",
        "content": final_content,
    })

# 保存到历史（自动裁剪超出 20 条的旧消息）
append_messages(thread_id, turn_messages)
```

**技术要点**：

- **双缓冲分工**：`tool_call_args_buffer` 是流式缓冲（TOOL_CALL_ARGS 发送后即清空）；`tool_call_full_args` 是完整 args 缓冲（不清空），专门供保存历史使用，避免参数在流式发送后丢失
- **args 归一化**：缓冲中的 args 是 JSON 字符串，保存前 `json.loads` 转为 dict，以通过后续 Pydantic 校验
- **工具调用记录兜底**：存在 tool_call_id 但无 args 缓冲时，仍以 `{}` 占位保存工具调用记录，保证 assistant(tool_call) → tool(result) 的历史结构完整
- **无文本回答兜底**：如果 Agent 未产生文本回答，仍会补发 `TEXT_MESSAGE_START` + 默认文本 + 保存无文本消息的历史

### 9.4 消息格式转换

[conversation_history.py#L42-L54](file:///d:/AiAgent/my-rag-demo/conversation_history.py#L42-L54) — `to_langchain_messages()` 将存储的 `MessageRecord[]` 转为 Agent 接受的格式：

```python
def to_langchain_messages(records: list[dict]) -> list[dict]:
    """将会话历史转为 LangGraph Agent 可接受的 messages 输入格式"""
    _parse_tool_calls(records)   # 预先修复历史中可能的字符串类型 args
    messages = []
    for r in records:
        msg = {"role": r["role"], "content": r["content"]}
        if r["role"] == "assistant" and r.get("tool_calls") and len(r["tool_calls"]) > 0:
            msg["tool_calls"] = r["tool_calls"]   # 带工具调用信息的 AI 消息
        if r["role"] == "tool" and r.get("tool_call_id"):
            msg["tool_call_id"] = r["tool_call_id"]  # 工具结果消息
        messages.append(msg)
    return messages
```

### 9.5 与现有 SSE 事件流的兼容性

多轮对话的改造**完全不影响**现有的 SSE 事件发送逻辑：

| 层面       | 改动前                                              | 改动后                       |
| ---------- | --------------------------------------------------- | ---------------------------- |
| SSE 事件   | `TOOL_CALL_START/ARGS/RESULT/END`、`TEXT_MESSAGE_*` | 完全不变                     |
| Agent 逻辑 | `agent.astream({ messages })`                       | 不变，仅 `messages` 数组变长 |
| 前端兼容性 | 按 AG-UI 标准接收事件                               | 无需任何修改                 |

唯一的变化是传给 Agent 的 `messages` 数组长度 — 从 1 条变为 N 条（含历史）。

### 9.8 边界处理

| 场景                     | 处理方式                                                                                     |
| ------------------------ | -------------------------------------------------------------------------------------------- |
| **首次对话（历史为空）** | `get_or_create_history()` 返回空列表，`full_messages` 仅含新消息                             |
| **历史超过 20 条**       | `append_messages()` 自动丢弃最早的消息（FIFO）                                              |
| **不同 threadId 并发**   | 每个 `threadId` 独立存储（`dict`），互不干扰                                                |
| **旧数据兼容**           | `_parse_tool_calls()` 原地将历史中字符串类型的 `tool_calls[].args` 修复为 dict               |
| **工具调用记录回溯**     | `tool_call_full_args`（完整 args 缓冲，不清空）在保存历史时按 `tool_call_id` 直接取用，流式缓冲 `tool_call_args_buffer` 发送后即清空 |
| **Agent 未产生文本回答** | 兜底逻辑：发送"抱歉，我暂时没有生成有效的回复，请换个说法再试一次。"文本，同时仍保存无文本消息的历史。supervisor 另有兜底路由：LLM 未输出有效路由且最新消息为未处理的 human 消息时，强制转交 general，避免"连续问候"场景零输出 |
