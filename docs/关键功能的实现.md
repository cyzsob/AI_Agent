### 1.3 PDF 文件解析（混合模式）

PDF 的解析是最复杂的，因为 PDF 可能同时包含**可选择文本**（文字型）和**图片中的文字**（扫描件/含截图）。

本项目实现了一个 **三层混合解析策略**：

#### 架构

```
PDF 文件
  │
  ├──→ PyMuPDF (fitz) 逐页提取可选择文本
  │       (page.get_text())
  │
  └──→ PyMuPDF 渲染每页为图像
          │
          └──→ RapidOCR 识别图片文字
                  (内置中英文模型，无需语言包)
                      │
                      智能合并策略：
                      ├ 文本 ≥ 80 字符 + 有 OCR  → 文本 + 图片 OCR 追加
                      ├ 文本 ≥ 80 字符 + 无 OCR  → 纯文本
                      ├ 文本 < 80 字符 + 有 OCR  → 纯 OCR（扫描件 PDF）
                      └ 两者都失败               → 返回有内容的那一路
```

#### 核心代码

```python
# app/ingestion/pdf_parser.py — PDF 混合解析
import numpy as np
import fitz  # PyMuPDF

MIN_TEXT_LENGTH = 80  # 低于此值认为 PDF 以图片为主，优先使用 OCR

def parse_pdf(file_path: str) -> str:
    doc = fitz.open(file_path)
    text_parts, ocr_parts = [], []

    for page in doc:
        # ---- 提取可选择文本 ----
        page_text = page.get_text().strip()
        if page_text:
            text_parts.append(page_text)

        # ---- 渲染为图片 + OCR ----
        pix = page.get_pixmap(matrix=fitz.Matrix(2.0, 2.0))  # 2x 分辨率
        img = np.frombuffer(pix.samples, dtype=np.uint8).reshape(
            pix.height, pix.width, pix.n
        )
        if pix.n == 4:
            img = img[:, :, :3]  # RGBA → RGB
        ocr_page_text = _ocr_page(img)
        if ocr_page_text:
            ocr_parts.append(ocr_page_text)

    return merge_text("\n".join(text_parts), "\n\n".join(ocr_parts))
```

#### 智能合并

```python
# app/ingestion/pdf_parser.py — merge_text（逻辑与 Node 版 mergeText 一致）
def merge_text(text_content: str, ocr_text: str) -> str:
    text_len = len(text_content or "")
    ocr_len = len(ocr_text or "")

    if text_len >= MIN_TEXT_LENGTH and ocr_len > 0:
        # 文字型 PDF + 含图片：合并两者，用分隔符标明
        return text_content + "\n\n--- 以下为图片 OCR 内容 ---\n" + ocr_text
    elif text_len >= MIN_TEXT_LENGTH:
        return text_content          # 文字型 PDF，无 OCR 内容
    elif ocr_len > 0:
        return ocr_text              # 图片型 PDF（扫描件），优先使用 OCR
    else:
        return text_content or ocr_text or ""  # 两路均失败，返回有内容的一路
```

#### 关键依赖

| 包                | 版本      | 用途                               | 平台兼容                 |
| ----------------- | --------- | ---------------------------------- | ------------------------ |
| `pymupdf` (fitz)  | ≥1.24     | PDF 解析、文本提取、页面渲染       | ✅ 纯 Python + 预编译二进制 |
| `rapidocr`        | ≥2.0      | OCR 文字识别（内置中英文模型）     | ✅ 基于 onnxruntime，无需训练数据 |
| `numpy`           | ≥1.26     | 图像数组转换与通道处理             | ✅ 预编译二进制          |
| `python-docx`     | ≥1.1      | DOCX 文档解析                      | ✅ 纯 Python             |

#### 技术要点

- **PyMuPDF 一库多用**：同时承担文本提取（`page.get_text()`）和页面渲染（`get_pixmap()`），无需额外的 pdfjs worker，无版本冲突问题
- **2x 缩放渲染**：`fitz.Matrix(2.0, 2.0)` 以 2 倍分辨率渲染页面，显著提升小字体的 OCR 识别率
- **RGBA → RGB**：RapidOCR 需要 3 通道输入，`pix.n == 4` 时截取前 3 通道
- **OCR 引擎复用**：模型加载耗时数秒，使用模块级单例 + 惰性初始化，避免每次解析都重新加载
- **兼容 rapidocr 2.x / 3.x**：`_ocr_page` 同时兼容 `(result, elapse)` 元组和 `RapidOCROutput` 对象两种返回格式
- **内置语言模型**：RapidOCR 内置中英文识别，无需像 Tesseract 那样准备 `chi_sim.traineddata` 语言包

### 实现代码

```python
# app/ingestion/sync.py — 文档分块（逐文件进行）
from langchain_text_splitters import RecursiveCharacterTextSplitter

splitter = RecursiveCharacterTextSplitter(
    chunk_size=200,
    chunk_overlap=20,
)

raw_doc = Document(page_content=content, metadata={"source": rel})
chunks = splitter.split_documents([raw_doc])

# 写入增强元数据（便于诊断与按文件清理）
for i, chunk in enumerate(chunks):
    chunk.metadata.update({
        "file_hash": sha,
        "chunk_index": i,

```

### 核心参数

| 参数           | 值  | 说明                                                     |
| -------------- | --- | -------------------------------------------------------- |
| `chunk_size`   | 200 | 每个块的最大字符数。保证块足够小，便于精确检索           |
| `chunk_overlap`| 20  | 相邻块之间的重叠字符数。防止一个完整语义被切分到两个块中 |

### 分块流程

```
原始文档（完整内容）
  → RecursiveCharacterTextSplitter
    → 首先按 "\n\n"（段落分隔）尝试分割
    → 如果块仍大于 chunk_size，按 "\n"（行分隔）继续分割
    → 如果还大，按 句号/问号等（句分隔）继续分割
    → 最后按 空格 或 字符 粒度分割
  → 输出 N 个 Document 对象，每个包含 page_content + metadata
```

### 数据持久化

使用 `PGVector.add_documents()` 将分块向量化后存入 PostgreSQL：

```python
# app/ingestion/sync.py — 嵌入模型 + 向量库初始化
from langchain_ollama import OllamaEmbeddings
from langchain_postgres import PGVector

embeddings = OllamaEmbeddings(
    model="bge-m3",                # 中英文优化的嵌入模型
    base_url="http://localhost:11434",  # 本地 Ollama 服务
)

vector_store = PGVector(
    embeddings=embeddings,
    collection_name="documents",
    connection="postgresql+psycopg://user:pass@host:5432/dbname",
    use_jsonb=True,
)
```

每个文件的入库流水线为 **删旧 → 嵌入入库 → 更新注册表**：

```python
# app/ingestion/sync.py — 单个文件入库流水线
import uuid

# 1) 先删除该文件的旧 chunks（按 cmetadata->>'source' 定位，新增时无旧数据无副作用）
delete_chunks_by_source(conn, rel)
conn.commit()

# 2) 向量化 + 入库
vector_store.add_documents(chunks, ids=[str(uuid.uuid4()) for _ in chunks])

# 3) 更新文件注册表（记录内容指纹，供下次增量判断）
upsert_registry(conn, rel, sha, file_path.stat().st_size, len(chunks))
conn.commit()
```

`langchain_postgres` 的 PGVector 实际写入两张表：

- `langchain_pg_collection`：集合表，记录 `name="documents"`
- `langchain_pg_embedding`：向量表，每行包含 `id`、`collection_id`、`document`（文本）、`cmetadata`（JSON 元数据）、`embedding`（bge-m3 生成的 1024 维向量）

> **注意**：后续 BM25 索引构建（见第三节）正是从 `langchain_pg_embedding` 表读取数据，两处数据源必须一致。

### 增量同步机制（新增 / 更新 / 删除文档）

以文件内容 **sha256 指纹** + 注册表表 `doc_file_registry`，将入库从"全量重灌"改造为**幂等增量同步**：

| 场景     | 判断依据                 | 处理方式                                            |
| -------- | ------------------------ | --------------------------------------------------- |
| 新增文档 | 路径不在注册表中         | 解析 → 分块 → 嵌入入库 → 写入注册表                 |
| 修改文档 | 路径在但内容哈希不一致   | 先删旧 chunks → 重新分块嵌入 → 更新注册表哈希       |
| 删除文档 | 注册表有、磁盘已消失     | 仅 `--prune` 时：删 chunks + 删注册表行             |
| 未变化   | 路径与内容哈希都一致     | 跳过（幂等）                                        |

注册表表结构（app/ingestion/sync.py 内 `CREATE TABLE IF NOT EXISTS` 幂等建表）：

```sql
CREATE TABLE IF NOT EXISTS doc_file_registry (
    file_path   TEXT PRIMARY KEY,          -- 相对 documents/ 的路径（当前即文件名）
    file_hash   TEXT NOT NULL,             -- sha256(文件字节)
    file_size   BIGINT NOT NULL,           -- 文件字节数
    chunk_count INT  NOT NULL DEFAULT 0,   -- 该文件生成的 chunk 数
    updated_at  TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

CLI 参数：

| 参数        | 说明                                                           |
| ----------- | -------------------------------------------------------------- |
| （无参数）  | 默认增量同步（幂等），只处理新增/修改的文件                     |
| `--rebuild` | 先清空向量库与注册表，再全量重建（schema/嵌入模型变更时使用）   |
| `--prune`   | 清理磁盘上已删除文档对应的 chunks 与注册表记录（默认关闭，防误删） |

> **升级兼容性**：首次运行增量同步时注册表为空，所有文件都会当作"新增"处理；而新增路径会**先按 source 删旧 chunks 再插入**，因此历史重复/旧版本数据会被自动清理，无需手工清库。

## 三、混合检索 (Hybrid Search)

### 实现位置

[app/rag/retriever.py](file:///d:/AiAgent/my-rag-demo/app/rag/retriever.py) + [app/rag/reranker.py](file:///d:/AiAgent/my-rag-demo/app/rag/reranker.py)

### 整体架构

```
用户查询
  │
  ├──→ 向量检索 (PGVector + bge-m3)     →  按语义相似度排序
  │
  ├──→ BM25 检索 (rank_bm25 内存索引)   →  按关键词匹配度排序
  │
  └──→ RRF 融合 (Reciprocal Rank Fusion)
       → 融合两路结果，按加权排名得分重新排序 → 候选池（5 条）
       → Cross-Encoder 重排 (bge-reranker-base)
       → 返回最终 Top-K 文档片段
```

### 3.1 向量检索

**技术要点**：

- **嵌入模型**：bge-m3（BAAI 出品），支持中英文，输出 1024 维向量
- **向量数据库**：PostgreSQL + pgvector 插件，存储向量并支持余弦相似度搜索
- **查询向量缓存**：每次检索都对查询调用本地 Ollama 嵌入（CPU 上单次数百 ms），相同/相似查询（多轮追问、多人问同一问题）会反复触发；`_QUERY_EMBEDDING_CACHE` 以"规范化后的查询文本"为键缓存向量（容量 512，超限整体清空），命中时直接用缓存向量做 PG 检索，大幅缩短检索延迟
- **同步 → 异步**：`similarity_search` 是同步阻塞调用，在异步检索器中用 `asyncio.to_thread` 放入线程池执行，避免阻塞事件循环

### 3.2 BM25 检索

使用 `rank_bm25` 的 `BM25Okapi` 实现，纯 Python、零外部依赖。

```python
# app/rag/retriever.py — 中文分词
import re

def tokenize_for_bm25(text: str) -> str:
    """在中文汉字之间插入空格，使 BM25 将每个汉字作为独立 token 索引。
    英文/数字保持原样，按空格分词。"""
    text = re.sub(r"([\u4e00-\u9fff\u3400-\u4dbf\uf900-\ufaff])", r" \1 ", text)
    text = re.sub(r"\s+", " ", text)
    return text.strip().lower()
```

```python
# app/rag/retriever.py — BM25 检索器
import numpy as np
from rank_bm25 import BM25Okapi

class BM25Retriever(BaseRetriever):
    def __init__(self, bm25_index: BM25Okapi, doc_map: dict, k: int = 6):
        super().__init__()
        self._bm25 = bm25_index
        self._doc_map = doc_map
        self._k = k

    async def _get_relevant_documents(self, query: str, **kwargs):
        processed_query = tokenize_for_bm25(query).split()
        scores = self._bm25.get_scores(processed_query)

        top_indices = np.argsort(scores)[::-1][: self._k]
        docs = []
        for idx in top_indices:
            if scores[idx] <= 0:
                continue
            doc_id = list(self._doc_map.keys())[idx]
            doc_data = self._doc_map[doc_id]
            docs.append(Document(
                page_content=doc_data["pageContent"],
                metadata={**doc_data["metadata"], "bm25Score": float(scores[idx])},
            ))
        return docs
```

**技术要点**：

- **为什么选 rank_bm25**：纯 Python 实现，零外部依赖，原生实现 Okapi BM25 算法，适合 demo 数据量级
- **中文分词策略**：在汉字前后插入空格，使每个汉字作为独立 token 索引。这是针对中文 BM25 的合理近似，能有效匹配关键词中的字序列
- **内存索引**：服务启动时从数据库加载全部文档，在内存中构建 BM25 索引（`BM25Okapi(tokenized_corpus)`），每次查询直接计算得分，速度快
- **零分过滤**：得分 ≤ 0 的文档直接跳过（BM25 对完全不匹配的词返回 0）

### 3.3 RRF 融合 (Reciprocal Rank Fusion)

```python
# app/rag/retriever.py — RRF 融合
import hashlib

def _doc_key(doc: Document) -> str:
    """统一的文档去重键：基于内容哈希。

    向量检索返回的 doc 无 dbId（metadata 仅为入库时的 cmetadata），
    BM25 检索返回的 doc 有 dbId，同一 chunk 在两路的键必须一致才能正确去重，
    因此统一使用内容哈希而非 dbId / 内容前缀。"""
    return hashlib.md5(doc.page_content.encode("utf-8")).hexdigest()


def rrf_merge(vector_docs, bm25_docs, final_k=3, rrf_k=60,
              vector_weight=0.5, bm25_weight=0.5):
    score_map = {}

    # 向量结果：按排名打分
    for i, doc in enumerate(vector_docs):
        doc_id = _doc_key(doc)
        if doc_id not in score_map:
            score_map[doc_id] = {"doc": doc, "score": 0.0}
        score_map[doc_id]["score"] += vector_weight / (rrf_k + i + 1)

    # BM25 结果：按排名打分
    for i, doc in enumerate(bm25_docs):
        doc_id = _doc_key(doc)
        if doc_id not in score_map:
            score_map[doc_id] = {"doc": doc, "score": 0.0}
        score_map[doc_id]["score"] += bm25_weight / (rrf_k + i + 1)

    # 按融合得分降序排列，并把融合分写回 doc 元数据（便于诊断）
    merged = sorted(score_map.values(), key=lambda x: x["score"], reverse=True)
    for item in merged:
        item["doc"].metadata["rrfScore"] = item["score"]

    return [item["doc"] for item in merged[:final_k]]
```

**RRF 公式**：

```
score(doc) = vectorWeight / (rrfK + rank_vector) + bm25Weight / (rrfK + rank_bm25)
```

**默认参数**：

| 参数            | 值  | 说明                                        |
| --------------- | --- | ------------------------------------------- |
| `rrfK`          | 60  | 融合常数，防止排名差异过大的文档得分趋近于0 |
| `vectorWeight`  | 0.5 | 向量检索权重                                |
| `bm25Weight`    | 0.5 | BM25 检索权重                               |
| `vectorK`       | 6   | 向量检索取 Top-6（app/agent/__init__.py 中配置为 10）    |
| `bm25K`         | 6   | BM25 检索取 Top-6（app/agent/__init__.py 中配置为 10）   |
| `rerankCandidates` | 5   | 融合后交给重排器的候选池大小（app/agent/__init__.py 中配置为 5，见下方说明） |
| `finalK`        | 3   | 重排后最终返回 Top-3                        |

**为什么 RRF 有效**：

- 一个文档同时在两路检索中排名靠前时，融合得分会叠加，排名更高
- 向量检索擅长**语义匹配**（"AI 公司的开源策略" → 命中"MIT 协议"相关段落）
- BM25 擅长**关键词精确匹配**（"DeepSeek-V4" → 精确命中包含该词组的段落）
- RRF 融合取两者之长，即使某一路检索表现差，另一路也能兜底

**Python 版与 JS 版的去重差异**：JS 版使用 `metadata.dbId` 或内容前缀作为去重键；Python 版统一使用 **内容 MD5 哈希**，因为向量检索返回的 doc 不带 `dbId`，两路的键必须一致才能正确去重。

### 3.4 Cross-Encoder 重排（新增能力）

重排是 Python 版新增的一层，弥补 bi-encoder（bge-m3）无法细粒度比较候选片段的不足：

```python
# app/rag/reranker.py — Cross-Encoder 重排器
from sentence_transformers import CrossEncoder

class CrossEncoderReranker:
    def __init__(self, model_name="BAAI/bge-reranker-base",
                 max_length=512, batch_size=16, device=None):
        self._model_name = model_name
        self._max_length = max_length
        self._batch_size = batch_size
        self._device = device
        self._model = None  # 惰性加载，首次调用时从 HuggingFace 下载权重

    async def rerank(self, query, docs, top_k=None):
        if not docs:
            return []
        try:
            scores = await asyncio.to_thread(self._predict, query, docs)
        except Exception as err:
            print(f"[Reranker] 重排失败，按原顺序返回候选: {err}")
            return docs  # 兜底：重排失败不拖垮主流程

        ranked = sorted(zip(scores, docs), key=lambda pair: pair[0], reverse=True)
        ordered = []
        for score, doc in ranked:
            doc.metadata["rerankScore"] = score
            ordered.append(doc)
        return ordered[:top_k] if top_k else ordered
```

**技术要点**：

- **逐对打分**：将 `(query, doc.page_content)` 组成 pair 输入 CrossEncoder，直接输出相关性分数，比 bi-encoder 更精细
- **惰性加载**：`_model` 首次调用才加载（需下载权重），避免服务启动变慢
- **失败兜底**：模型加载或推理失败时打印警告并按原顺序返回，保证 RAG 主流程不被重排拖垮
- **线程池**：`CrossEncoder.predict` 是同步阻塞调用，用 `asyncio.to_thread` 放入线程池

### 3.5 混合检索器并行执行 + 重排

```python
# app/rag/retriever.py — HybridRetriever._get_relevant_documents
async def _get_relevant_documents(self, query, **kwargs):
    # 并行执行向量检索（sync→线程池，含查询向量缓存）和 BM25 检索（async）
    def _vector_search():
        embedding = self._embed_query_cached(query)
        return self._vector_store.similarity_search_by_vector(
            embedding, k=self._vector_k
        )

    vector_docs, bm25_docs = await asyncio.gather(
        asyncio.to_thread(_vector_search),
        self._bm25_retriever._get_relevant_documents(query),
    )

    # RRF 融合 → 候选池（不直接截断到 final_k，先放大候选供重排）
    candidates = rrf_merge(
        vector_docs, bm25_docs,
        final_k=self._rerank_candidates,   # 先取 5 条候选
        rrf_k=self._rrf_k,
        vector_weight=self._vector_weight,
        bm25_weight=self._bm25_weight,
    )

    # Cross-Encoder 重排（可选）→ 最终 Top-K
    if self._enable_rerank and self._reranker is not None and candidates:
        return await self._reranker.rerank(query, candidates, top_k=self._final_k)

    return candidates[: self._final_k]
```

**关键设计**：

- **`asyncio.gather` 并行执行两路检索**，相互等待而非串行，总耗时 ≈ max(向量检索, BM25 检索)
- **查询向量缓存**：向量检索前先查 `_QUERY_EMBEDDING_CACHE`，命中则跳过 Ollama 嵌入调用，直接 `similarity_search_by_vector`
- **候选池放大**：RRF 融合先取 `rerankCandidates=5` 条，而不是直接截断到 3 条，给重排器更多候选做精细排序（CPU 上 CrossEncoder 逐对推理耗时随候选数线性增长，候选从 10 降到 5 可显著缩短检索延迟，RAG 质量损失极小）
- **两级排序流水线**：`向量/BM25 各自 Top-10 → RRF 融合 Top-5 → Cross-Encoder 重排 Top-3`

### 5.1 整体思路

本项目将"单 ReAct Agent（一个模型 + 全部工具混杂）"升级为 **Planner 规划器模式的多 Agent 系统**（不新增任何依赖，基于已安装的 `langgraph` 手写 StateGraph 实现）：

- 一个 **planner 任务规划器**：LLM 将用户问题（结合精简后的对话历史）拆解为**结构化子任务**（JSON：`id / target / instruction / depends_on / summary`），按依赖关系分发：
  - 无依赖 → **`Send` 并行分发**到各 `worker_<name>` 节点（LangGraph 动态扇出）
  - 有依赖 → **executor 串行执行**各 worker 子图
- 多个 **专业 worker Agent**（按工具域划分，各持独立工具子集 + 领域专用提示词）：

| worker 节点 | 职责 | 持有工具 |
| ----------- | ---- | -------- |
| `knowledge` | 知识/检索 | `get_deepseek_info`、`search_kb` |
| `devops`    | Gitee 平台操作 | `gitee_*` 等 MCP 工具 |
| `general`   | 天气 + 日常闲聊 | `get_weather` |

- 一个 **summarizer 汇总器**：整合各 worker 写入 `task_results` 的结论 + 原始问题，生成**唯一透出给用户**的最终回答

核心收益：每个 worker 只面对自己领域的少量工具，且只收到**自己的私有指令**（看不到原始问题与其他 worker 内容），决策更聚焦；无依赖任务并行执行降低总延迟；最终回答由汇总器统一整合，消除多 worker 回答重复/冗余的问题。

> **与旧版（严格串行 Supervisor + `TransferTo*`/`handoff_to_*` 交接）的关键差异**：① 每个 worker 只收到自己的私有指令（HumanMessage），看不到原始问题与其他 worker 内容；② 无依赖任务并行执行（LangGraph `Send` 动态扇出）；③ 最终回答由汇总器统一整合，worker 原始文本不再直接透出给用户；④ 移除 `TransferTo*/handoff_to_*` 交接机制（planner 承担任务拆分）。

```python
class MultiAgentState(TypedDict):
    messages: Annotated[list, add_messages]  # 完整对话历史（planner 上下文 / 汇总参考 / 历史保存）
    tasks: list[dict]                        # planner 拆解的任务列表
    task_results: Annotated[dict, operator.or_]  # 各 worker 结果（并行分支天然线程安全）
    original_query: str                      # 本轮原始用户问题（仅汇总器与日志使用）
```

2. **planner 节点**：LLM 按 `PLANNER_PROMPT` 输出 JSON 任务列表，经 `_parse_planner_json` 容错解析（剥离 Markdown 围栏、按括号配平提取首个对象）；随后校验 target 是否为活跃成员、同一 target 的任务合并为一个、无有效任务时**兜底交给 general**。planner 输入只喂最近 3 条 worker 结论（截断 300 字符）+ 最新问题，避免全量历史导致 TTFT 与成本膨胀。

3. **条件边分发**（`_make_route_dispatch`）：无依赖 → 返回 `Send(node, {"messages": [HumanMessage(instruction)]})` 列表，LangGraph 动态扇出并行执行；存在依赖 → 返回 `"executor"` 走串行路径。

4. **worker 节点安全封装**（[app/agent/supervisor.py#L421-L447](file:///d:/AiAgent/my-rag-demo/app/agent/supervisor.py#L421-L447)）：每个 worker 子图包一层 try/except，单个 worker 内部工具异常不拖垮整轮；结果提取**直接在节点源头完成**（`_extract_worker_result` 取子图最后一条带文本的 AI 消息），写入 `task_results` 的独立键——并行 Send 分支汇聚到 join 前会合并全部 messages，若靠事后 collect 节点读共享 state 会读到其他 worker 的输出（knowledge 结果曾被 devops 覆盖）。

5. **executor 串行路径**：按 planner 给出的依赖顺序命令式调用 worker 子图（该路径下工具事件不流入 SSE，仅最终汇总文本输出；串行场景较少见，正确性优先）。

6. **summarizer 汇总节点**：以原始问题 + 各 worker 结论（失败部分标注"未能完成"）生成最终回答，直接返回模型响应消息本身（保持 message id 稳定，routes.py 按 id 去重，避免 langgraph 对同一条消息重复发射流事件）。

### 5.7 planner 拆解推理示例

```
用户: "DeepSeek V4 用什么架构？顺便查下北京天气"
  → planner 拆解（无依赖 → 并行分发）:
      [
        {id: task_knowledge, target: knowledge, instruction: "DeepSeek V4 用什么架构？", depends_on: null},
        {id: task_general,   target: general,   instruction: "查询北京当前天气",        depends_on: null}
      ]
  → Send 并行分发
  → knowledge worker 调用 search_kb({query: "DeepSeek V4 架构"})
      → 混合检索：向量 + BM25 → RRF → Cross-Encoder 重排 → 结论
  → general worker 调用 get_weather({city: "北京"}) → 实时天气数据
  → join → summarizer 整合为一段完整回复 → END

用户: "DeepSeek 开源战略怎么样？"
  → planner → 单任务 {target: knowledge, instruction: "DeepSeek 开源战略怎么样？"}
  → knowledge worker 调用 get_deepseek_info() → 读取 deepseek介绍手册.txt 全文 → 结论
  → summarizer 整合 → END

用户: "你好"
  → planner → 单任务 {target: general}
  → general worker 直接友好回答，无工具调用 → summarizer 整合 → END

用户: "帮我在 Gitee 上搜索 changelink 的开源项目"
  → planner → 单任务 {target: devops}
  → devops worker 输出 tool_call: gitee_* → MCP Server 执行 → 结论
  → summarizer 整合 → END
```

**多 Agent 的优势**：

- **任务级并行**：无依赖子任务通过 `Send` 并行执行，总耗时 ≈ max(各 worker) 而非串行累加
- **信息隔离**：每个 worker 只收到私有指令，看不到原始问题与其他 worker 内容，避免工具误用
- **回答统一**：最终回答由 summarizer 整合，worker 原始文本（含过程性描述）不透出，杜绝重复/冗余
- **避免不必要的 token 消耗**：planner 只喂精简上下文，闲聊类问题直接由 general 处理，无需检索
- **按域定制提示词**：每个 worker 的 prompt 独立定制（如 knowledge 强制区分"公司整体"与"技术细节"两种工具）
- **灵活扩展**：新增专业 Agent 只需在 `app/agent/supervisor.py` 加一个节点 + `_worker_prompt`，在 `app/agent/__init__.py` 分组处补充工具前缀

### 6.1 SSE 协议

使用 Server-Sent Events (SSE) 实现逐 token 流式输出，遵循 AG-UI 协议标准。事件类型枚举与格式化工具独立抽取到 [app/api/sse.py](file:///d:/AiAgent/my-rag-demo/app/api/sse.py)：

```python
# app/api/sse.py — AG-UI 事件类型枚举 + SSE 格式化
from enum import StrEnum

class AgUiEventType(StrEnum):
    RUN_STARTED = "RUN_STARTED"
    RUN_FINISHED = "RUN_FINISHED"
    RUN_ERROR = "RUN_ERROR"
    TEXT_MESSAGE_START = "TEXT_MESSAGE_START"
    TEXT_MESSAGE_CONTENT = "TEXT_MESSAGE_CONTENT"
    TEXT_MESSAGE_END = "TEXT_MESSAGE_END"
    TOOL_CALL_START = "TOOL_CALL_START"
    TOOL_CALL_ARGS = "TOOL_CALL_ARGS"
    TOOL_CALL_RESULT = "TOOL_CALL_RESULT"
    TOOL_CALL_END = "TOOL_CALL_END"


def sse_event(data: dict) -> str:
    return f"data: {json.dumps(data, ensure_ascii=False)}\n\n"


# ========== 多 Agent 节点常量 ==========
SUPERVISOR_NODE = "supervisor"            # 兼容保留（Planner 模式下已无此节点）
SUMMARIZER_NODE = "summarizer"            # 汇总器节点：唯一向客户端透出最终回答文本的节点
TRANSFER_TOOL_NAMES: set[str] = set()     # Planner 模式已无 TransferTo*/handoff 工具
```

### 6.2 事件生命周期

```
RUN_STARTED                    → 告知客户端开始处理
  ├─ TOOL_CALL_START           → (可选) Agent 决定调用工具
  ├─ TOOL_CALL_ARGS            → (可选) 工具参数字典
  ├─ TOOL_CALL_RESULT          → (可选) 工具执行结果
  ├─ TOOL_CALL_END             → (可选) 工具生命周期结束
  │
  ├─ TEXT_MESSAGE_START        → 文本回复开始
  ├─ TEXT_MESSAGE_CONTENT      → 逐 token 推送文本内容（多次）
  ├─ TEXT_MESSAGE_END          → 文本回复结束
  │
RUN_FINISHED                   → 全部处理完成
```

### 6.3 聊天端点（核心流式处理）

多 Agent 图与单 Agent 的 `astream` 接口完全兼容。Planner 模式下有两个关键差异：

- 开启 **`subgraphs=True`**：事件为 `(ns, (chunk, metadata))` 三元结构，`ns` 为子图命名空间（顶层 planner/summarizer 节点为空元组，worker 子图内事件非空）
- **只有 summarizer 节点的文本会透出给客户端**；worker 子图的原始文本（`ns` 非空或节点名非 summarizer）一律隐藏，避免"冗余内容太多 / 重复回答"直接暴露给前端

```python
# app/api/routes.py — POST /api/chat（SSE 事件流）
stream = _agent_ref[0].astream(
    {"messages": full_messages},
    stream_mode="messages",
    subgraphs=True,
)

async for event in stream:
    # subgraphs=True 事件结构兼容处理
    if isinstance(event, tuple) and len(event) == 2 and isinstance(event[0], tuple):
        ns, (chunk, metadata) = event
    else:
        ns, chunk, metadata = (), *event
    node_name = metadata.get("langgraph_node") if metadata else None

    # ① Supervisor 节点（兼容保留）：仅内部路由，不透出事件、不进入历史
    if node_name == SUPERVISOR_NODE:
        continue

    # ② 工具执行结果（ToolMessage）：只按消息类型判断，不依赖节点名
    #    （嵌套子图下工具消息的节点名可能上报为外层节点名）
    if isinstance(chunk, ToolMessage):
        # is_internal_tool 过滤内部编排工具结果
        # 否则 → 按 tool_call_id 补发 TOOL_CALL_START / TOOL_CALL_RESULT / TOOL_CALL_END
        continue

    # ③ Worker/汇总器节点输出（文本 + 工具调用）
    #    注意：嵌套子图下 worker 输出是完整 AIMessage（非 AIMessageChunk），
    #    AIMessageChunk 是 AIMessage 的子类，统一按 AIMessage 处理
    if isinstance(chunk, AIMessage):
        # 工具调用 → tracker 累积 → TOOL_CALL_START / TOOL_CALL_ARGS
        for tc_id, tc_name, tc_args in iter_tool_call_pieces(chunk):
            ...

        # 文本内容：只透出汇总器节点的最终回答
        chunk_content = chunk.content if isinstance(chunk.content, str) else ""
        is_summarizer = (not ns) and node_name == SUMMARIZER_NODE
        if chunk_content and not is_summarizer:
            pass  # 隐藏 worker 子图原始文本（ns 非空或节点名非 summarizer）
        elif chunk_content:
            final_content += chunk_content
            # → TEXT_MESSAGE_START / TEXT_MESSAGE_CONTENT（逐 token）

    # 流结束后：只保存 user 消息 + 汇总器最终回答到历史
    # → 发送 TEXT_MESSAGE_END / RUN_FINISHED
```

**多节点适配的关键点**：

1. **`subgraphs=True` 事件解构**：多 Agent 图含嵌套子图时事件为 `(ns, (chunk, metadata))` 三元组，需先按 tuple 结构解包；顶层 planner/summarizer 节点的 `ns` 为空元组。
2. **summarizer 文本唯一透出**：`is_summarizer = (not ns) and node_name == SUMMARIZER_NODE`——只有顶层汇总器节点输出的文本才推给客户端并累积到 `final_content`；worker 子图原始文本隐藏（避免"冗余内容太多 / 重复回答"直接暴露）。
3. **工具消息去节点名依赖**：工具执行结果只按 `isinstance(chunk, ToolMessage)` 判断（原 `node_name == "tools"` 在嵌套子图下不可靠），按 `tool_call_id` 键控；ToolMessage 先于 TOOL_CALL_START 到达时补发 START。
4. **Worker 输出统一按 `AIMessage` 处理**：嵌套 subgraph 的 worker 输出是**完整 `AIMessage`**（含 dict 形态的 `tool_calls`）而非流式 `AIMessageChunk`，借助 `iter_tool_call_pieces(chunk)` 兼容两种形态（`tool_call_chunks` / `tool_calls`，每项可能是 dict 或对象）。

### 6.4 TOOL_CALL_ARGS 的缓冲机制

工具参数可能是逐 token 产生的流式片段，也可能是 worker 一次性输出的完整 dict，直接发送会导致前端收到碎片化 JSON。这部分逻辑抽取到 [app/api/stream.py](file:///d:/AiAgent/my-rag-demo/app/api/stream.py) 的 `ToolCallTracker` 类：**按 `tool_call_id`（UUID，全局唯一）键控**，通过累积 args + **JSON 完整性检测**，只在 args 完整时才一次性发送：

```python
# app/api/stream.py — ToolCallTracker 使用方式
tracker = ToolCallTracker()

for tc_id, tc_name, tc_args in iter_tool_call_pieces(chunk):
    # 内部编排工具过滤
    if is_internal_tool(tc_name or ""):
        continue

    # TOOL_CALL_START — 只在首次出现时发送
    if tc_id and not tracker.is_registered(tc_id):
        tracker.register(tc_id, tc_name)
        yield sse_event({"type": AgUiEventType.TOOL_CALL_START,
                         "toolCallId": tc_id, "toolCallName": tc_name})

    # 累积参数
    tracker.accumulate_args(tc_id, tc_args)

# 检测 JSON 是否完整 → 一次性发送（发送后清空流式缓冲）
for event_str in tracker.flush_complete_args_events(sse_event):
    yield event_str
```

`ToolCallTracker` 内部维护的状态：

| 状态字段          | 用途                                             |
| ----------------- | ------------------------------------------------ |
| `_tool_call_ids`  | 已发送 TOOL_CALL_START 的 tool_call_id 集合（去重） |
| `_args_buffer`    | 流式 args 累积（TOOL_CALL_ARGS 发送后清空）       |
| `_full_args`      | 完整 args 累积（不清空，供保存历史使用）          |
| `_name_buffer`    | tool_call_id → 工具名                             |
| `_tool_messages`  | 收集工具返回消息（历史保存用）                    |

流结束后 `flush_remaining_args_events()` 兜底发送所有未完成的缓冲 args。

```python
# app/main.py — FastAPI App 工厂 + Lifespan
@asynccontextmanager
async def _lifespan(app: FastAPI):
    agent, tools, disconnect_fn = await _agent_init()
    try:
        yield
    finally:
        await disconnect_fn()   # 断开所有 MCP 连接

def create_app() -> FastAPI:
    app = FastAPI(title="DeepSeek RAG Agent", lifespan=_lifespan)
    app.add_middleware(CORSMiddleware, allow_origins=["*"], ...)
    from app.api.routes import router
    app.include_router(router)
    return app
```

**技术要点**：

- **FastAPI 替代 Express**：`StreamingResponse(media_type="text/event-stream")` 天然支持 SSE 流式响应
- **lifespan 管理**：Agent 和检索器在应用启动时初始化（注入全局 `_agent_ref`），关闭时清理 MCP 连接
- **`/capabilities` 端点**：声明服务器 AG-UI 能力（streaming=True, persistentState=True, tools=True），并声明 `multimodal.input.image=True`（见第十节）
- **流式模式**：`agent.astream(stream_mode="messages", subgraphs=True)` 返回 `(ns, (chunk, metadata))`，通过 `metadata["langgraph_node"]` + `ns` 区分顶层节点与 worker 子图

### 关键技术亮点总结

1. **多 Agent 协同（Planner 规划器模式）** — planner 将问题拆解为结构化子任务，无依赖任务 `Send` 并行分发、有依赖 executor 串行执行，最后由 summarizer 统一整合唯一透出；worker 只收到私有指令、原始文本不透出
2. **混合检索 (向量 + BM25 + RRF + Cross-Encoder 重排)** — 兼顾语义匹配和关键词精确匹配，两路并行执行 + 加权排名融合 + 交叉编码器精排 + 查询向量缓存
3. **Worker 自主决策（ReAct）** — 每个 worker 是 LangGraph ReAct Agent，按私有指令与工具返回内容自主回答，告别固定链路
4. **Query Rewriting** — 用 LLM 将口语化问题改写为检索友好表达，提升检索准确率
5. **RRF 融合算法** — 按排名倒数加权，消除两路检索评分尺度不一致的问题
6. **SSE 流式输出** — 逐 token 推送，支持工具调用事件和文本内容的实时渲染；worker 子图文本隐藏，仅 summarizer 最终回答透出
7. **本地嵌入** — Ollama + bge-m3 本地运行，零外部 API 依赖，低延迟
8. **MCP 标准化工具接入** — 通过 MCP 协议统一接入外部工具，配置文件驱动，零代码扩展；自动发现工具列表并包装为 LangChain StructuredTool
9. **基于 threadId 的多轮对话** — 会话历史管理器按 threadId 保存每轮 user 消息 + 汇总器最终回答，支持追问和指代消解；Token 计数滑动窗口防止溢出
10. **文档增量同步入库** — 以文件内容 sha256 为指纹 + 注册表表，新增/修改/删除文档幂等增量入库；`POST /api/admin/sync` + `refresh_retriever()` 让运行中的服务无需重启即可检索最新数据
11. **多模态图片理解** — 用户上传图片经智谱 GLM-4V 生成文字描述，与文本合并后进入既有纯文本 Agent/RAG 链路（详见第十节）

#### 步骤 3：自动包装为 LangChain 工具

[app/mcp/client.py#L102-L142](file:///d:/AiAgent/my-rag-demo/app/mcp/client.py#L102-L142) — 将 MCP Tool 自动包装为 LangChain 的 `StructuredTool`：

```python
# 3. 为每个 MCP Tool 创建 LangChain 工具
for mcp_tool in tools:
    # 加前缀防命名冲突（如 gitee_*）
    tool_name = f"{name}_{mcp_tool.name}"

    # 将 JSON Schema 参数定义转换为 Pydantic model
    input_schema = mcp_tool.input_schema
    pydantic_model = json_schema_to_pydantic(input_schema) if input_schema else create_model("EmptyInput")

    # 创建工具调用函数（用工厂函数避免闭包共享循环变量）
    def build_call_tool(srv_name, tool_name, sess):
        async def call_tool(**kwargs) -> str:
            result = await sess.call_tool(name=tool_name, arguments=kwargs)
            parts = [c.text for c in result.content if hasattr(c, "text")]
            return "\n".join(parts)
        return call_tool

    wrapped_tool = StructuredTool.from_function(
        name=tool_name,
        description=mcp_tool.description or "",
        args_schema=pydantic_model,
        coroutine=build_call_tool(name, mcp_tool.name, session),
    )
    langchain_tools.append(wrapped_tool)
```

JSON Schema → Pydantic 的转换（[app/mcp/client.py#L19-L58](file:///d:/AiAgent/my-rag-demo/app/mcp/client.py#L19-L58)）：

```python
def json_schema_to_pydantic(input_schema: dict) -> type[BaseModel]:
    """将 MCP 的 JSON Schema 参数定义转为 Pydantic model"""
    if not input_schema or "properties" not in input_schema:
        return create_model("EmptyInput")

    properties = input_schema.get("properties", {})
    required_fields = input_schema.get("required", [])

    fields = {}
    for key, prop in properties.items():
        prop_type = prop.get("type", "string")
        description = prop.get("description", "")
        is_required = key in required_fields

        # JSON Schema 类型 → Python 类型
        py_type = {"string": str, "number": float, "integer": int,
                   "boolean": bool, "array": list, "object": dict}.get(prop_type, str)

        if is_required:
            fields[key] = (py_type, Field(description=description))
        else:
            fields[key] = (py_type, Field(default=None, description=description))

    return create_model("ToolInput", **fields)
```

**关键技术点**：

| 步骤            | 说明                                                                                           |
| --------------- | ---------------------------------------------------------------------------------------------- |
| **加前缀**      | 防止不同 MCP Server 的工具名冲突（如 gitee_* 与 github_*）                   |
| **Schema 转换** | 将 MCP 的 JSON Schema 参数定义转换为 Pydantic model（`create_model` 动态创建），适配 `StructuredTool` |
| **调用代理**    | `call_tool` 内部调用 `session.call_tool()`，通过已建立的 stdio 连接发送 JSON-RPC 请求           |
| **闭包隔离**    | 用 `build_call_tool` 工厂函数生成闭包，避免 Python 循环中闭包共享循环变量的经典陷阱             |
| **结果提取**    | MCP 标准返回格式为 `{ content: [{ type, text }] }`，拼接所有 text 内容                          |

## 九、Agent 多轮对话详解

### 实现位置

[app/agent/history.py](file:///d:/AiAgent/my-rag-demo/app/agent/history.py) + [app/api/routes.py](file:///d:/AiAgent/my-rag-demo/app/api/routes.py)

### 9.1 问题背景

改造前，服务器每次请求都只将最后一条 user 消息传给 Agent：

```python
# 改造前 — 无历史记忆
stream = _agent.astream(
    {"messages": [{"role": "user", "content": user_message}]},
    stream_mode="messages",
)
```

这导致 Agent 每次对话都是"第一次见面"，无法理解"它"、"那个"等指代，也无法支持追问。

### 9.2 解决方案：基于 threadId 的历史管理

实现核心思路：

```
Turn 1:
  客户端 POST { threadId: "sess-1", messages: [user_msg_1] }
    → 历史为空 → 仅传 user_msg_1 给 Agent
    → Agent 执行 → 收集本轮消息 → 保存到会话历史

Turn 2:
  客户端 POST { threadId: "sess-1", messages: [user_msg_2] }
    → 加载历史 [user_msg_1, ai_msg_1, ...]
    → 构造完整消息 [user_msg_1, ai_msg_1, user_msg_2] 传给 Agent
    → Agent 理解上下文 → 收集本轮消息 → 追加到会话历史
```

### 9.3 关键步骤

#### 步骤 1：会话历史管理器

[app/agent/history.py](file:///d:/AiAgent/my-rag-demo/app/agent/history.py) 提供核心数据结构：

```python
# 内存存储结构
_sessions: dict[str, list[dict]] = {}   # dict[threadId, list[MessageRecord]]

# MessageRecord 格式（可序列化的 plain dict）
{
  "role": "user" | "assistant" | "tool",
  "content": str,
  # assistant 消息带工具调用时
  "tool_calls": [{"id", "name", "args"}] | None,
  # tool 消息带工具调用 ID
  "tool_call_id": str | None,
}
```

导出的函数：

| 函数                                 | 说明                                             |
| ------------------------------------ | ------------------------------------------------ |
| `get_or_create_history(thread_id)`   | 获取或创建会话历史                               |
| `to_langchain_messages(records)`     | 将 `MessageRecord[]` 转为 Agent 可接受的输入格式 |
| `append_messages(thread_id, messages)` | 追加本轮消息到历史（基于 tiktoken 精确 Token 计数的滑动窗口裁剪） |
| `clear_history(thread_id)`           | 清除指定会话的历史                               |

**上下文窗口管理**：

```python
# app/agent/history.py
MAX_HISTORY_TOKENS = 100_000   # 约 DeepSeek V4 128K 上下文的 80%，用 tiktoken 精确计数

# append_messages 中的自动裁剪逻辑（Token 计数滑动窗口）
def append_messages(thread_id: str, messages: list[dict]) -> None:
    history = get_or_create_history(thread_id)
    history.extend(messages)
    # Token 计数裁剪：从头部丢弃旧消息，直到满足上限
    while len(history) > 1 and _count_total_tokens(history) > MAX_HISTORY_TOKENS:
        # 如果第二条是 user 消息（常见的 user→assistant 对），
        # 先跳过第二条，尝试丢弃更早的消息（保持至少一组完整对话）
        if len(history) >= 4 and history[1]["role"] == "user":
            history.pop(0)
            continue
        # 保底：确保不会把最后一条 user 消息裁掉
        remaining_users = [m for m in history[1:] if m["role"] == "user"]
        if not remaining_users:
            # 只剩第一条是 user → 保留它，丢弃当前的
            break
        history.pop(0)
    _sessions[thread_id] = history
```

#### 步骤 2：加载历史 + 构造完整消息

[app/api/routes.py#L149-L158](file:///d:/AiAgent/my-rag-demo/app/api/routes.py#L149-L158) — 在每次请求时加载历史并构造完整消息数组：

#### 步骤 3：传递完整消息给 Agent

#### 步骤 5：保存本轮消息到历史

```python
# ========== 保存本轮消息到历史 ==========
# 只保存 用户消息 + 汇总器的最终回答（不保存 worker 的工具调用记录与
# 工具结果，避免旧 tool_call 痕迹干扰后续轮次的 planner 与历史 token 膨胀）
turn_messages = [user_message_record]
if final_content:
    turn_messages.append({
        "role": "assistant",
        "content": final_content,
    })

append_messages(thread_id, turn_messages)
```

**技术要点**：

- **历史精简**：Planner 模式下只保存 user 消息 + 汇总器最终回答——worker 的工具调用记录与工具结果不进历史，避免旧 tool_call 痕迹干扰后续轮次的 planner 任务拆解，同时防止历史 token 膨胀
- **SSE 事件不受影响**：工具调用事件（TOOL_CALL_START/ARGS/RESULT/END）仍然实时推给前端，只是不再写入会话历史
- **无文本回答兜底**：如果 Agent 未产生文本回答，仍会补发 `TEXT_MESSAGE_START` + 默认文本 + 保存无文本消息的历史

### 9.4 消息格式转换

[app/agent/history.py#L69-L80](file:///d:/AiAgent/my-rag-demo/app/agent/history.py#L69-L80) — `to_langchain_messages()` 将存储的 `MessageRecord[]` 转为 Agent 接受的格式：

```python
def to_langchain_messages(records: list[dict]) -> list[dict]:
    """将会话历史转为 LangGraph Agent 可接受的 messages 输入格式"""
    _parse_tool_calls(records)   # 预先修复历史中可能的字符串类型 args
    messages = []
    for r in records:
        msg = {"role": r["role"], "content": r["content"]}
        if r["role"] == "assistant" and r.get("tool_calls") and len(r["tool_calls"]) > 0:
            msg["tool_calls"] = r["tool_calls"]   # 带工具调用信息的 AI 消息
        if r["role"] == "tool" and r.get("tool_call_id"):
            msg["tool_call_id"] = r["tool_call_id"]  # 工具结果消息
        messages.append(msg)
    return messages
```

### 9.5 与现有 SSE 事件流的兼容性

多轮对话的改造**完全不影响**现有的 SSE 事件发送逻辑：

| 层面       | 改动前                                              | 改动后                       |
| ---------- | --------------------------------------------------- | ---------------------------- |
| SSE 事件   | `TOOL_CALL_START/ARGS/RESULT/END`、`TEXT_MESSAGE_*` | 完全不变                     |
| Agent 逻辑 | `agent.astream({ messages })`                       | 不变，仅 `messages` 数组变长 |
| 前端兼容性 | 按 AG-UI 标准接收事件                               | 无需任何修改                 |

唯一的变化是传给 Agent 的 `messages` 数组长度 — 从 1 条变为 N 条（含历史）。


### 9.8 边界处理

| 场景                     | 处理方式                                                                                     |
| ------------------------ | -------------------------------------------------------------------------------------------- |
| **首次对话（历史为空）** | `get_or_create_history()` 返回空列表，`full_messages` 仅含新消息                             |
| **历史 Token 数超过 100K**       | `append_messages()` 自动丢弃最早的消息（滑动窗口裁剪，保证至少保留最近一条 user 消息）              |
| **不同 threadId 并发**   | 每个 `threadId` 独立存储（`dict`），互不干扰                                                |
| **旧数据兼容**           | `_parse_tool_calls()` 原地将历史中字符串类型的 `tool_calls[].args` 修复为 dict               |
| **工具事件与历史解耦**   | `ToolCallTracker` 的 `_full_args`（完整 args，不清空）仅供流式事件与调试使用；历史不再保存工具调用记录，`flush_remaining_args_events()` 兜底发送未完成缓冲 |
| **Agent 未产生文本回答** | 兜底逻辑：发送"抱歉，我暂时没有生成有效的回复，请换个说法再试一次。"文本，同时仍保存无文本消息的历史。planner 另有兜底：解析失败或无有效任务时强制拆解为单任务交给 general，避免"连续问候"场景零输出 |

### 实现位置

- [app/services/multimodal.py](file:///d:/AiAgent/my-rag-demo/app/services/multimodal.py) — 云端 GLM-4V 视觉模型封装（图片字节 → 文字描述）
- [app/services/message.py](file:///d:/AiAgent/my-rag-demo/app/services/message.py) — AG-UI 多模态消息解析与图片理解编排

### 10.1 整体思路

本项目的主链路（Agent / RAG / 工具）是**纯文本**的。为了让用户上传图片也能参与问答，采用 **"图片 → 文字化"** 策略：

1. 解析 AG-UI 用户消息中的 `content` 数组（可能同时含 `text` 和 `image` 两种 part）
2. 将图片交给**云端智谱 GLM-4V 视觉模型**（默认免费模型 `glm-4v-flash`）生成详细文字描述
3. 把描述与用户文字合并为纯文本 user 消息，进入既有文本链路——**无需改造 Agent/RAG 的任何逻辑**

```
用户消息 content part
  ├─ {type:"text", text:"这张图里的趋势是什么？"}
  └─ {type:"image", source:{type:"data"|"url", value:...}}
        │
        ▼  extract_text_and_images()（兼容新旧两种消息格式）
   (user_text, image_parts)
        │
        ▼  describe_images()（asyncio.gather 并发调用 GLM-4V）
   [图片1描述, 图片2描述, ...]
        │
        ▼  compose_multimodal_message()
   "用户问题\n\n[图片1]: 描述...\n[图片2]: 描述..."
        │
        ▼  纯文本进入现有 Agent/RAG 链路（与普通文本请求无异）
```

### 10.2 关键实现

#### 消息解析（app/services/message.py）

AG-UI 协议经历了格式演进，解析器需**同时兼容新旧两种格式**：

```python
# app/services/message.py — 提取文本与图片
def extract_text_and_images(content) -> tuple[str, list[dict]]:
    # 纯字符串 content → 直接返回文本
    if isinstance(content, str):
        return content, []

    text_parts, image_parts = [], []
    for part in content:
        ptype = part.get("type")
        if ptype == "text":
            text_parts.append(str(part.get("text", "")))
        elif ptype == "image":
            src = part.get("source") or {}
            stype = src.get("type")
            if stype == "data":                      # 新版：内联 base64
                image_parts.append({"bytes": base64.b64decode(strip_data_uri(src.get("value")))})
            elif stype == "url":                     # 新版：URL 图片
                image_parts.append({"url": src.get("value")})
            elif part.get("data"):                   # 旧版 BinaryInputContent 兼容
                image_parts.append({"bytes": base64.b64decode(strip_data_uri(part["data"]))})
            elif part.get("url"):
                image_parts.append({"url": part["url"]})
    return "\n".join(text_parts).strip(), image_parts
```

| 格式版本          | 图片 part 结构                                             |
| ----------------- | ---------------------------------------------------------- |
| 新版（2025-10）   | `{type:"image", source:{type:"data"\|"url", value, mimeType?}}` |
| 旧版（兼容）      | `{type:"image", data:<base64>, mimeType, url?}`            |

#### 并发描述（app/services/message.py）

多张图片通过 `asyncio.gather` **并发**调用视觉模型；单张失败只返回错误提示文本（`图片N 理解失败：...`），不中断整体请求，保证文本部分照常回答。

### 10.4 技术要点

- **零改造接入**：图片先"文字化"再进入纯文本链路，Agent/RAG/工具完全无感知，多模态能力可随时关闭（不配置 `ZHIPU_API_KEY` 时上传图片会返回明确错误提示）
- **并发描述**：多张图片用 `asyncio.gather` 并发调用 VLM，总耗时 ≈ max(单张) 而非串行累加
- **图片缩放**：最长边超过 1024px 时等比压缩为 JPEG（quality=88），大幅降低 VLM 视觉 token 数量与传输体积；解码失败原样返回交给 VLM 侧容错
- **大小与超时保护**：URL 图片下载上限 10MB（防恶意/异常大图打爆内存）、超时 120s（云端 GPU 推理通常 1-3s，留足余量）
- **失败兜底**：单张图片描述失败只影响该图片，返回 `（图片N 理解失败：...）` 文本，整体请求照常完成
- **URL 图片来源**：支持 `http(s)` URL 图片自动下载（带超时 + 大小上限 + 重定向跟随）
