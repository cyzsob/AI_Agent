# 上下文记忆模块设计方案（Redis + PGVector）

> 设计目标：通过 Redis 分层管理长短期上下文记忆；异步多线程在每轮交互后将长期记忆持久化至向量数据库；短期记忆采用文本摘要提取，长期记忆支持语义 + 全文混合检索；设置 distance 阈值保证提取上下文的精确度。
>
> 状态：**已实现并通过端到端验证**（Redis 短期记忆 / PGVector 长期记忆 / 混合检索 / 阈值过滤 / 降级均验证通过）。

---

## 1. 设计背景

当前项目的会话历史（`app/agent/history.py`）为**进程内 dict 存储**，存在两个问题：

1. 服务重启后对话历史全部丢失；
2. 历史只做"滑动窗口裁剪"（tiktoken 计数），裁剪掉的内容无法再被利用。

本方案引入 **Redis（短期记忆）+ PGVector（长期记忆）** 两级记忆体系，让对话具备跨会话、跨重启的"记忆能力"。

---

## 2. Redis 本地部署（Docker）

```powershell
# 拉取并启动 Redis 7（映射默认端口 6379）
docker run -d --name rag-redis --restart unless-stopped -p 6379:6379 redis:7-alpine

# 验证连通性，返回 PONG 即成功
docker exec -it rag-redis redis-cli ping

# 常用运维命令
docker logs rag-redis          # 查看日志
docker restart rag-redis       # 重启
```

Python 客户端：`pip install redis`（依赖写入 `pyproject.toml`，`redis>=5`）。

配置项（`.env` 新增）：

```
REDIS_URL=redis://localhost:6379/0
MEMORY_DISTANCE_THRESHOLD=0.6     # 余弦距离阈值，保证提取精度
MEMORY_RETRIEVAL_K=5              # 长期记忆混合检索 Top-K
SHORT_MEMORY_TTL=3600             # 短期记忆闲置过期时间（秒）
```

## 3. 总体架构

```
每轮对话结束
    │
    ▼
┌─────────────────────────────────────────────────────────┐
│ 短期记忆 (Redis) —— 热数据，读写快，带 TTL                 │
│  · memory:short:{thread_id}:messages  最近 N 轮原文 (List) │
│  · memory:short:{thread_id}:summary   滚动摘要 (String)    │
└──────────────┬──────────────────────────────────────────┘
               │ 异步任务（asyncio + 线程池，不阻塞 SSE 响应）
               ▼
┌─────────────────────────────────────────────────────────┐
│ 长期记忆 (PGVector) —— 冷数据，语义持久化                 │
│  ① LLM 文本摘要提取（DeepSeek）                           │
│  ② bge-m3 向量化（Ollama，1024 维）                       │
│  ③ 写入 memory_long 表（sha256 指纹去重）                 │
└─────────────────────────────────────────────────────────┘
               ▲
               │ 下一轮构建 prompt 时检索（同步、快）
┌─────────────────────────────────────────────────────────┐
│ 混合检索：向量(余弦距离 < 阈值) + 全文(tsvector/BM25)     │
│ → RRF 融合 → distance 阈值过滤 → 注入上下文              │
└─────────────────────────────────────────────────────────┘
```

**分工原则**：Redis 管"快而短"，向量库管"慢而久"，异步线程负责两者之间的搬运。

## 4. 数据设计

### 4.1 Redis Key 规划（短期记忆）

| Key | 类型 | 内容 | TTL |
|---|---|---|---|
| `memory:short:{thread_id}:messages` | List | 最近 20 条消息原文（含 role/content） | 1 小时，每次访问刷新 |
| `memory:short:{thread_id}:summary` | String | 滚动摘要文本（LLM 对已滑出窗口内容的压缩） | 1 小时，每次访问刷新 |

- 用 List + `LTRIM` 限制长度；
- 用 `EXPIRE` 实现闲置过期；
- 摘要由 LLM 对滑出窗口的内容做**文本摘要提取**，窗口裁剪后不丢关键信息。

### 4.2 PGVector 表（长期记忆）

```sql
CREATE TABLE IF NOT EXISTS memory_long (
    id          BIGSERIAL PRIMARY KEY,
    thread_id   TEXT NOT NULL,                 -- 归属会话
    content     TEXT NOT NULL,                 -- 摘要/关键事实文本
    embedding   vector(1024),                  -- bge-m3
    fingerprint TEXT UNIQUE,                   -- sha256(content)，幂等去重
    created_at  TIMESTAMPTZ DEFAULT now()
);
CREATE INDEX ON memory_long USING hnsw (embedding vector_cosine_ops);
```

## 5. 模块拆解（新增 `app/memory/` 包）

| 文件 | 职责 |
|---|---|
| `redis_store.py` | Redis 连接池（`redis.asyncio`）+ 短期记忆读写：追加消息、LTRIM 限长、读写滚动摘要、刷新 TTL、清理会话 |
| `summarizer.py` | 调 DeepSeek 对滑出窗口的消息做**文本摘要提取**（一句话/要点列表），返回结构化摘要 |
| `long_term.py` | 异步持久化管线：摘要 → bge-m3 向量化 → 写入 `memory_long`，sha256 去重；内部用 `asyncio.to_thread` 跑阻塞的 LLM/embedding 调用 |
| `retriever.py` | 长期记忆**混合检索**：query 向量检索（pgvector，`vector_cosine_ops`）+ 全文检索（PostgreSQL tsvector 或复用 rank_bm25），RRF 融合，**distance 阈值过滤**，返回 Top-K 注入 prompt |

---

## 6. 核心时序（一次对话）

```
1. 请求进入 → 从 Redis 取短期记忆（messages + summary），构建历史上下文
2. 同步触发长期记忆检索：混合召回 → 距离阈值过滤 → 相关记忆拼入 system prompt
3. Agent 正常走现有 LangGraph 流程（历史存储替换为 Redis）
4. 响应结束（RUN_FINISHED 后）→ 追加本轮消息到 Redis，裁剪窗口
5. 调度异步任务（asyncio.create_task）：滑出窗口部分 → LLM 摘要 → 向量化 → 写 memory_long
6. 全程不阻塞 SSE 响应；失败仅记日志，不影响主流程
```

---

## 7. 检索与阈值策略

- **语义检索**：query 经 bge-m3 编码，与 `memory_long.embedding` 算余弦距离，取 Top-K；
- **全文检索**：PostgreSQL `pg_trgm`/`tsvector` 或复用项目现成的 `rank_bm25`，保关键词精确命中；
- **RRF 融合**：沿用现有 `app/rag/retriever.py` 的公式 `score = 0.5/(60+rank_vec) + 0.5/(60+rank_bm25)`；
- **distance 阈值**：bge-m3 余弦距离默认 `0.6`（可配置），**融合后仍超阈值的记忆直接丢弃**，宁可少用不可用错，保证提取精度；
- **降级策略**：检索失败或无命中时，静默降级为"无长期记忆"模式，不影响主对话。

## 9. 测试方案（实现后分步验证）

1. **Redis 层**：`docker exec rag-redis redis-cli ping` → PONG；Python 脚本 `redis.asyncio` 写入/读取/TTL 过期验证；
2. **短期记忆**：起服务，同 `threadId` 连发 2 轮对话 → 查 `memory:short:*` key 存在、消息正确、超 TTL 自动消失；
3. **长期记忆**：第 2 轮结束后等 1-2 秒 → 查 `memory_long` 表出现新行，且重复对话不再产生重复行（指纹去重生效）；
4. **混合检索**：写一条"我叫小明"类记忆 → 新会话用同义表述（"我的名字"）提问 → 验证语义路召回；用精确关键词 → 验证全文路召回；两者 RRF 融合后注入 prompt；
5. **阈值过滤**：调低 `MEMORY_DISTANCE_THRESHOLD` → 无关记忆被过滤，prompt 中不出现；
6. **降级验证**：停掉 Redis 容器 → 对话仍可用（只是无记忆），日志记录告警。

---

## 10. 关键取舍说明

- 短期记忆放 Redis：读写高频、要求低延迟、需要 TTL 自动清理；
- 长期记忆放 PGVector：需存 embedding 并支持相似度检索，与现有 RAG 基础设施（langchain-postgres/pgvector/asyncpg）复用；
- 异步线程池：保证"摘要 + 向量化 + 入库"的耗时（秒级）不拖慢用户响应（毫秒级）。
